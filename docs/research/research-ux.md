## 0. 结论摘要（先看这六条）

1. **核心对象不在导航里，也不在榜单里。** `/stations` 只出现在页脚（`Layout.tsx:168`）和侧栏（`Feed.tsx:104`），`/rank` 只出现在页脚；而首页排行榜的三个 tab 是「模型 / 社区 / 达人」（`RankingBoard.tsx:11-15`），没有站点。用户对产品的第一印象会是「一个模型资讯站」，而中转站是导购对象。
2. **导航有 2 个条目在指向同一份内容。** `/community` 与 `/reviews` 都由 `FeedPage` 渲染（`Feeds.tsx:4-14`），只是 `kind` 固定不同，而组件本身已经支持切换类型（`Feed.tsx:37-45`）。两条导航占了两格，却没换来两倍的信息量；这正好是腾给「中转站」的那一格。
3. **生产环境是空站，而空态表达分不清「还没内容」和「筛选没匹配」。** 三个列表页对完全空库都显示「没有符合条件的…」（`Stations.tsx:70`、`Models.tsx:54`、`Search.tsx:18`），排行榜干脆没有任何空态（`RankingBoard.tsx:91-96`），会渲染出一个空白的 `.rank-grid`。这是「看起来像坏了」的主因。
4. **11 个新功能里，有 6 个的正确落点是「已经在的页面加一处操作区」，不需要新页面**：编辑/删除/举报进 `PostDetail.tsx:32-50` 与 `Comments.tsx:89-117`，Token 兑换进 `Me.tsx:16-23` 的 tab 集，注销进 `Me.tsx:109-145` 表单下方，头像进同一个 Settings 表单，对比进 `/stations` 的卡片与浮条。只有「通知中心」值得一个新路由。
5. **头像不要走上传，也不要外链。** `server/src/static.ts:14` 的 CSP 是 `img-src 'self' data:`，外链头像会被浏览器直接拦掉；没有对象存储，本地上传只能把 base64 塞进 SQLite，而 `Author` 对象会随每条评论、每篇文章一起返回（`domain.ts:54`，评论每页 20 条 `Comments.tsx:53`）。推荐「首字母色块 + 12 个预设印章图标」。
6. **最该先改的 3 个交互问题**：① 排行榜无空态、三列表格也无「全空」态（站点是核心对象却永远空着）；② 补录模型 / 推荐新站提交成功后跳到 `/me?tab=posts`（`Submit.tsx:70`、`Submit.tsx:110`），而结果在「我的投稿」标签（`Me.tsx:21`），用户会落到「还没有分享」并以为提交失败；③ Agent 凭证「吊销」按钮零确认直接执行（`AgentTokens.tsx:91` → `37-50`），这是全站唯一一个不可逆的写操作，而新功能（删文章、删评论、注销）全是这一类，必须先立一个统一的确认组件。

## 1. 现状导航诊断

### 1.1 走查：第一次打开，想找中转站要几步

按真实首屏元素顺序（`Home.tsx:66-82`：`hero-grid` → `RankingBoard` → `feed-layout`）：

| 步 | 用户看到什么 | 能不能到达中转站 | 代码依据 |
|---|---|---|---|
| 0 | 顶部导航：首页 / 模型 / 社区 / 评测；右侧 API文档 / 商务合作 / 投稿分享 / 登录\|注册 | **不能**。四个主项里没有站点 | `Layout.tsx:138-141`、`144-146` |
| 1 | 搜索框，placeholder「搜索模型、厂商、中转站」 | 只有知道站名才有用 | `Layout.tsx:51` |
| 2 | 首屏三栏：厂商列表 / Banner / 用户卡 | **不能**。三栏里没有任何「站点」入口 | `Home.tsx:71-75` |
| 3 | 排行榜 6 张卡（模型 / 社区 / 达人 tab） | **不能**。站点不在榜单 tab 里 | `RankingBoard.tsx:11-15` |
| 4 | 信息流「值得蹬」第一屏卡片 | 勉强：卡片右下角偶尔有站名链接 | `PostCard.tsx:50-52` |
| 5 | 继续往下，右侧栏「热门中转站」→「全部站点」 | **能**（桌面端）。但侧栏在信息流右侧、排行榜之下 | `Feed.tsx:101-105` |
| 6 | 滚到页脚 → 中转站库 | **能**，但是全页最后一个模块 | `Layout.tsx:168` |

结论：

- **桌面端**：从首页进入「中转站库」需要向下滚动约 2 屏（排行榜 + 信息流首屏），然后点一次侧栏或页脚链接。任何一步没看到，路径就断了。
- **移动端更糟**：`.feed-layout` 在 1040px 以下变单列（`home.css:283`），`.feed-side` 变成 `position: static`（`home.css:284`），于是「热门中转站」被推到整个信息流（最多 10 条卡片 + 加载更多）之后。移动端首页到站点库的实际路径是「一直滚到底」。
- **唯一「一步可达」的路径是搜索**，而搜索要求用户已经知道站名——这是老用户路径，不是新用户路径。

一句话：**这个站把品味层面的入口（模型、社区、评测）放在第一层，把交易层面的入口（中转站、报价、排行榜）埋在第三层。而它的产品定位是「导购」。**

### 1.2 六个结构性问题

**① 核心对象缺位，且是双重缺位。**
`/stations` 不在主导航（`Layout.tsx:135-159`）；站点也不在榜单（`RankingBoard.tsx:11-15` 只有 model / community / expert）。而 `/rank` 自己也不在主导航，只在页脚（`Layout.tsx:169`）和首页模块的「查看更多」（`RankingBoard.tsx:89`）。结果：**这是全站唯一既有列表页、又有详情页、又有对比数据、又有投票收藏评论区，却进不了导航的对象。**

**② 导航里有一对冗余项。**
`/community` 与 `/reviews`（`App.tsx:27-28`）渲染同一个 `FeedPage`（`Feeds.tsx:4-14`），唯一区别是 `kind`。`Feed` 组件在没有 `fixedKind` 时自带类型切换器（`Feed.tsx:37-45`，`FEED_KINDS` 包含 deal / review / guide / community）。所以「评测」这一格的信息量等于「社区」页里的一个 tab。

**③ 右上角的投稿下拉漏掉了 4 种类型。**
`ShareMenu` 只有「发爆料 / 写评测」两项（`Layout.tsx:68-69`），而 `/submit` 支持 6 种（`Submit.tsx:14-22`：deal / review / guide / community / model / station）。其中**「推荐新站」是唯一能补充核心对象供给的入口，却没有任何导航曝光**，只能从 `/submit` 里点第四个 radio 才能发现（`Submit.tsx:163-175`）。这也是 `Feed.tsx:111` 空态里「推荐一个」按钮指向 `/submit`（不带 kind）时的不一致：进去默认是「发爆料」（`Submit.tsx:34`），而不是推荐新站。

**④ 页脚与主导航重复三项。**
「模型库 / API 文档 / 商务合作」在导航（`Layout.tsx:139`、`144`、`145`）和页脚（`Layout.tsx:170-172`）各出现一次。页脚应承担「导航里放不下的东西」和「信任相关」两类内容，重复项挤占了它本可以给「中转站库 / 排行榜 / 对比」的位置。

**⑤ 详情页没有面包屑，从外链进来不知道自己在哪。**
`StationDetailPage`（`Stations.tsx:95-105`）和 `PostDetail`（`PostDetail.tsx:32-42`）的页头只有标题和自己的元信息，没有回到列表的链接。站点详情页里**没有任何一处链回 `/stations`**——用户从搜索结果或分享链接落地后，只能靠浏览器后退。

**⑥ 全站没有 skip link，`<main>` 无 id。**
`Layout.tsx:191` 是 `<main className="container site-main">`，没有 `id="main"`，页首也没有「跳到主内容」。键盘用户每次换页都要 Tab 穿过 logo、搜索框、热搜最多 10 个链接（`Layout.tsx:16-18` 热词数量由接口决定）、5 个导航项、2 个下拉，才能到正文。新功能如果继续往导航里加东西，这个成本只会更高。

### 1.3 方案 A：平铺（最小改动，推荐先做）

**主导航左组（5 项）**

```
首页 / 中转站 / 模型 / 社区 / 排行榜
```

- 新增「中转站」→ `/stations`，放在「首页」之后，第二位。
- 新增「排行榜」→ `/rank`。理由：`/rank` 是唯一把「模型 / 社区 / 达人」三个榜合成一页的地方（`Rank.tsx:15`），也是首页模块「查看更多」的落点（`RankingBoard.tsx:89`），它现在只能从页脚进，点完「查看更多」后再也回不到别处。
- 删除「评测」：`/reviews` 路由保留，`/community` 页面里默认就带类型切换（`Feed.tsx:37-45` 已经渲染，只是 `fixedKind` 时被隐藏）。把 `/reviews` 改成 `<Navigate to="/community?kind=review" replace />`，社区页读取 `?kind=` 作为初始值（现在 `Feed` 用内部 state `ownKind`，`Feed.tsx:23`，需要改成受控或从上取初值）。
- 右组：`投稿分享`（下拉）、`登录 | 注册` 保留；`API文档`、`商务合作` 降为次要项，桌面保留 15px 灰字（现状即如此，`chrome.css:42`），760px 以下**已经**被 `.nav-secondary` 隐藏（`chrome.css:118`），不动。

**页脚改为**

```
中转站库 · 排行榜 · 站点对比 · 模型库 · API 文档 · 商务合作 · 关于/免责声明
```

**投稿下拉补齐到 4 项**（`Layout.tsx:63-74`）：

```
发爆料 / 写评测 / 推荐新站 / 补录模型
```

「写指南」「发社区」留在 `/submit` 的类型选择器里即可——下拉是「用户有明确意图时的一步到位」，指南和社区没有明确意图，属于「我想写点什么」，走表单更自然。但**「推荐新站」必须进下拉**，它是供给入口。

### 1.4 方案 B：对象优先 + 二级（方案 A 的下一步）

把「中转站」做成一个带二级结构的栏目，而不是一个页面：

```
主导航：首页 / 中转站 / 模型 / 社区

「中转站」hover/focus 弹出或页内 tab：
  全部站点 | 排行榜 | 对比
```

- 站点库 `/stations` 顶部加一行页内导航（复用 `.tabs` / `role="tablist"` 的现有样式，`home.css:163-174`）：`全部站点 · 排行榜 · 对比`。`/rank` 变成 `/stations?view=rank`，`/compare` 变成 `/stations/compare`。
- 好处：用户永远在「中转站」这个语境里，切换视图不丢上下文；SEO 上 `/stations` 成为聚合页，权重集中。
- 代价：`/rank` 的旧链接必须兼容（见 1.5）；「排行榜」作为导航词本身有吸引力，藏进二级会掉点击。

**建议路径**：先上方案 A（改 3 个导航项、1 个下拉、1 个重定向），观察 `/stations` 的入口点击；再把「对比」做成 `/stations` 页内的选择模式（不占导航），最后视数据决定是否上方案 B 的二级结构。不要一步跳到 B。

### 1.5 代价与兼容

| 代价 | 具体影响 | 处理方式 |
|---|---|---|
| **老链接** | `/reviews` 有外链和搜索结果缓存；改成重定向后旧 URL 仍要能打开 | 客户端 `<Navigate replace>`（`Auth.tsx:58` 已有先例）。**不能**在服务端 301：`server/src/static.ts:25` 对所有非 `/api`、非 `/assets` 路径都直接返回 `index.html`，没有按路径重定向的能力，加一层 path→location 表反而要维护两份路由 |
| **软 404** | SPA 回退让 `/stations/不存在的站` 也返回 HTTP 200 + 404 页面 | 现在是 200；新加的对比页/通知页同样会软 404。SEO 阶段一起处理（见 2.7） |
| **SEO** | 现在每个页面只有一份全局 description（`web/index.html:7`），`<title>` 是 React 19 在组件里设的（如 `Stations.tsx:50`）。删「评测」等于让一个索引页消失 | 删之前先做 2.7 的 meta；`/reviews` 重定向后用 canonical 指到 `/community?kind=review` |
| **用户习惯** | 「评测」是内容型用户的入口词，从导航消失会掉发现率 | 社区页 tab 顺序调整为 `评测 · 爆料 · 指南 · 社区`（`Feed.tsx:12` 的数组顺序即渲染顺序），把评测放首位；首页信息流的类型切换器默认仍是爆料 |
| **移动端宽度** | 760px 以下导航是一行 46px（`chrome.css:113-119`），`.nav-link` 是 `white-space: nowrap`（`chrome.css:39`），`.nav-group` 间距 18px（`chrome.css:114`）。4 项时左组约 180px，右组「投稿分享 + 登录\|注册」约 120px，400px 宽刚好；加第 5 项会挤 | 删掉「评测」（省约 40px）再加「中转站」（约 55px），净增 15px，仍在余量内。**如果你要同时保留 评测 + 中转站 + 排行榜，760px 以下必须改成横向滚动导航**（照抄 `.vendor-list` 的做法，`home.css:292-294`），不要靠缩字号硬塞 |

### 1.6 不推荐的做法

- **把「中转站」做成首页的一个模块**（比如在排行榜下面加「热门站点」大卡）。首页已经有 4 个模块（三栏 / 排行榜 / 信息流 / 侧栏），再加就变成门户页，反而更找不到。侧栏已经有「热门中转站」（`Feed.tsx:101-128`），信息密度足够。
- **合并 `/rank` 进 `/stations` 但删掉 `/rank` 路由**。`RankingBoard` 在首页被复用（`Home.tsx:76`），`/rank` 只是它的完整版（`Rank.tsx:15` 传 `pageSize={12}`）。保留 URL 成本极低，删掉只会制造 404。

## 2. 每个新功能的界面落点

> 本节每个功能给三件事：**放哪**（文件:行号）、**什么形态**（组件级）、**状态怎么呈现**（含审核态/失败态/空态）。

### 2.1 Token 积分兑换

**现状**：Token 只在两处出现——首页用户卡的数字滚动条（`UserCard.tsx:130-134`）和「我的」页统计（`Me.tsx:215`）；只有签到发放（`state.tsx` 的 `checkIn`，`UserCard.tsx:111-123`）。没有任何「花」的路径。

**落点**：`/me` 新增一个 tab，**排在「账户设置」之前**。

```
My.tsx: TABS = [
  { value: 'favorites', label: '我的收藏' },
  { value: 'posts', label: '我的分享' },
  { value: 'submissions', label: '我的投稿' },
  { value: 'tokens', label: '我的 Token' },   // 新增
  { value: 'settings', label: '账户设置' },
]
```

**页面结构（`tab === 'tokens'`）**：

1. **余额卡**：大号数字（复用 `.me-stats` 的 `dd` 字号 20px/700，`pages.css:163`）+ 一行说明「签到每天 +N，连续签到加成」。右边一个 `去签到` 按钮；已签到则显示「今天已签到 · 连续 N 天」（文案照抄 `UserCard.tsx:144-146` 的已签到态，保持全站一致）。
2. **收支明细**：`.data-table`，列 = 时间 / 事由 / 变动（`+20` 绿色、`-300` 红色）。数据源新增 `GET /me/token-logs`。空态：「还没有记录。每天签到是唯一的来源。」
3. **兑换清单**：卡片网格，每张卡 = 名称 / 图标 / 消耗 / 「兑换」按钮。
   - 首个 SKU 强烈建议是**邀请码**：服务端已经有 `INVITE_CODES` 与邀请码表（`docs/spec.md` 的「管理接口」段），而 Agent 凭证的准入条件之一就是「持有有效邀请码」（`docs/spec.md` 的「账号与权限」段）。所以「Token → 邀请码 → 解锁 Agent 凭证」是一条现成的闭环，不需要新造库存。
   - 第二个 SKU：**昵称高亮色**（8 个取自 `visuals.tsx:38` 的 `ACCENTS`，直接复用取色逻辑）。
   - 第三个（可选）：**站点对比名额**——不要做。把功能当商品卖会让核心功能显得残缺。

**交互形态（不要 modal）**：点「兑换」→ 卡片原地展开一行确认条：

```
将消耗 300 Token（现余额 420 → 120）。兑换后不可退回。
[确认兑换]  [取消]
```

确认后**同一张卡原地替换**为结果块，复用 Agent 凭证明文的展示语言（`AgentTokens.tsx:67-76`）：「明文只显示一次」+ 只读输入框 + 点击全选（`onFocus={e => e.currentTarget.select()}`）+ 「已保存，隐藏」。

**错误态**：
- 余额不足 → 按钮 disabled，卡内文案「还差 180 Token，去签到」，「去签到」是可点的（不要只把按钮置灰，那是最常见的死路，`AgentTokens.tsx:65` 现在就有这个问题）。
- 并发扣减失败 → 卡片内 `.form-error` + `role="alert"`，余额重新拉取。

**不要**把兑换放进首页用户卡：`hero-grid > *` 固定 440px 高（`home.css:6`），移动端压成一行三列（`home.css:312-327`），没有空间。

### 2.2 文章编辑 / 删除

**落点 1：文章详情页操作区。**

`PostDetail.tsx:32-42` 的 `<header className="article-head">` 里，`.article-meta`（第 35-41 行）之后、`.article-summary`（第 43 行）之前，插入一行：

```
<div className="article-actions">
  作者可见： [编辑]  [删除]
  所有人可见： [举报]
</div>
```

- 视觉：一行 `text-btn`（12px 灰字，`base.css:101`），右对齐或左对齐随 meta；分隔用现有 `.article-meta` 的间距（4px 12px）。**不要**用 `btn btn-red`——创建动作才用红色，破坏性动作用文字按钮 + 确认弹窗。
- 可见性判定：`post.author.handle === me.data?.handle`。`Author` 带 handle（`domain.ts:54`），不需要新字段。未登录不渲染这一行（不要渲染成「登录后可编辑」）。
- 移动端：这一行会换行到 meta 下方，`pages.css:201-208` 的 `.article` padding 是 18px 14px，够放三个 12px 文字按钮。

**落点 2：列表卡片上的操作。**

`MyPosts`（`Me.tsx:97-107`）里每张 `PostCard` 增加一个右上角「⋯」按钮，菜单项 = `编辑 / 删除 / 查看审核状态`。**不要**在公共信息流的卡片上放编辑入口（`PostCard.tsx` 被 6 个页面复用，加作者判定会让这个组件对每个消费方都要知道当前用户）。

**落点 3：编辑表单。**

复用 `/submit`，加参数：`/submit?edit=<postId>`。

- `Submit.tsx:37` 的 `form` 初始值改为：有 `edit` 时从 `api.getPost(id)` 预填；`kind` 锁定，不显示类型选择器（`Submit.tsx:160-176` 隐藏 fieldset）。
- 页头标题（`Submit.tsx:156`）：「编辑投稿」；副文案（`Submit.tsx:157`）加一句「修改提交后需要重新审核，审核期间线上仍是上一版」。
- 提交按钮（`Submit.tsx:282`）：「提交修改」。
- 成功后 toast：「修改已提交，审核通过后替换线上版本」，跳 `/posts/<id>`（**不是** `/me`——用户刚改完，最想看的是自己的文章现在长什么样）。

**审核态怎么呈现（这是最容易做错的一处）**

现状：`PostDetail.tsx:23-24` 用两行 `demo-notice` 提示 pending / rejected；`PostCard.tsx:30-31` 用 tag 提示。**但「修改待审」和「初次投稿待审」语义完全不同**，不能共用文案。

新增第三种状态：文章已上线且有一版修改在审。呈现为：

- 详情页：`role="note"` 的窄条插在标题下方（复用 `.demo-notice` 的样式但换成 warn 色系）：「已提交修改，正在审核。线上仍是上一版，其他人看到的也是上一版。」
- 卡片：tag 从「审核中」改为「修改待审」。
- 「我的投稿」（`Me.tsx:37-77`）：这条记录的状态显示「修改待审」，并有「撤销修改」按钮（把 pending 的 submission 撤掉，线上版本不动）。
- **关键**：编辑已通过的文章时，**线上旧版本必须保持可见且可访问**。服务端把修改作为一条 pending submission 入队（队列已支持 `superseded`，`Me.tsx:27`），审核通过后整体替换。文案必须反复强调「线上还是旧版」——否则作者会以为文章消失了（待审文章只有作者可见，`PostDetail.tsx:23`）。

**删除的确认形态**：见 7.2 的确认弹窗规范。文案要说明「评论和投票会一起消失」。

### 2.3 评论删除

**落点**：`Comments.tsx:89-117` 每条顶层评论（`<li className="comment">`）。

在 `.comment-meta`（第 92-95 行）这一行，时间之后、行尾，加一个「⋯」按钮：

```
<p className="comment-meta">
  <strong>{nickname}</strong>
  <time>{date}</time>
  <button className="comment-more" aria-label={`${nickname} 的评论操作`} aria-haspopup="menu" aria-expanded={…}>⋯</button>
</p>
```

- 自己写的：「删除」。
- 别人的：「举报」。
- 回复（`Comments.tsx:104-115`，`CommentReply`）同样加，但回复只能删自己的，不提供「回复」按钮（现状回复本身就只有一层，不需要）。

**一层回复的提示文案（重点）**

删父评论时，回复不能跟着消失——那是别人的内容。所以：

- 父评论有回复时，确认框正文：

  > 删除后这条评论不再显示，但下面 2 条回复会保留，仍然能被看到。
  > 删除不可撤销。

- 删除后渲染占位，**不要**把整条 `<li>` 移除（否则回复会失去上下文）：

  ```
  [灰色头像] 该评论已删除
  └ 回复 1 …
  └ 回复 2 …
  ```

- 无回复时，确认框正文：「删除后不可恢复。」
- 删除成功后**焦点管理**：焦点移到该占位条的「⋯」消失后的下一个可聚焦元素；更稳妥的做法是把焦点移到评论区的 `<h2>`（`Comments.tsx:76`），并在评论区上方放一个 `aria-live="polite"` 的 `sr-only` 播报「评论已删除」。

**状态**：删除请求中按钮 disabled + 文案「删除中…」；失败时在评论条目内出一行 `.form-error`（不要用 toast——用户可能已经滚走了）。

### 2.4 举报

**入口（四处，共用同一个 `<ReportDialog>`）**：

1. 文章详情操作区（2.2 落点 1）的「举报」。
2. 评论「⋯」菜单（2.3）。
3. 站点详情 `.station-actions`（`Stations.tsx:100-103`，`VoteButtons` 与 `FavoriteButton` 之后）。
4. 卡片「⋯」菜单（选做：需要给 `PostCard` / `StationCard` 都加，收益不如前三个）。

**形态**：一个 `<dialog>`（原生 `showModal()`，自带焦点陷阱与 Esc），`role` 由元素本身提供，另加 `aria-labelledby` 指向标题。

字段：

```
举报内容：<被举报对象的标题/首句，单行截断>
原因（必选，radio）：
  ○ 垃圾广告或引流
  ○ 虚假/过期的报价
  ○ 人身攻击或辱骂
  ○ 侵权（盗图、洗稿）
  ○ 其他
补充说明（选填，200 字，textarea + 字数计数）
[提交举报]  [取消]
```

- 未登录点举报 → 走 `useRequireLogin()`（`state.tsx:45-54`）跳登录，登录后回到原页并**自动重新打开弹窗**（把 `?report=<targetId>` 写进 URL 或用 sessionStorage 记一次待办）。这是「登录后要继续原来的动作」的通用要求，现在全站没有一处做到（`FavoritesButton`、`VoteButtons` 都是登录后回到页面，用户得自己再点一次）。
- 提交后：弹窗内直接变结果态「已收到。处理结果会通过通知告诉你。」+ 关闭按钮；同一目标 24 小时内按钮变「已举报」并 disabled（服务端去重）。
- **不对被举报内容做任何即时隐藏或标记**，也不告诉用户「我们删了没有」以外的细节（避免被当作战术工具）。

**空态/边界**：不提供「举报自己」；不提供「举报理由」的预设只填一个字也能过——最少 1 个原因必选。

**入口分三层，互相不冲突：**

   选满 3 个后其余勾选框 disabled，并 toast「最多对比 3 个站」。

**结果页 `/compare?stations=a,b,c`**

- URL 可分享，2~3 个站；少于 2 个 → 页面显示引导态（不报错）。

  2. 模型报价：**按计价口径分组**，每组一张小表（沿用 `Models.tsx:104-111` 的说明：「只有同一计价口径之间才能比大小」）。同一模型在一行里横向对比，缺报价格子写「—」不是「暂无」（表格里「暂无」太长）。

### 2.7 SEO 元信息

**现状**：`web/index.html:7` 一条全局 description；`<title>` 由各页组件内的 React 19 `<title>` 元素设置（`Home.tsx:69`、`Stations.tsx:50`、`Models.tsx:88`、`PostDetail.tsx:21`、`Rank.tsx:14`、`Search.tsx:67`、`Docs.tsx:96`、`Business.tsx:4`、`NotFound.tsx:6`）。没有 canonical、没有 og、没有 robots.txt、没有 sitemap。

**落点 1：抽一个 `<PageMeta>` 组件**（放 `web/src/components/PageMeta.tsx`），替换所有裸 `<title>`：

```tsx
<PageMeta
  title="中转站库"
  description={`已收录 ${total} 个中转站，按倍率、可用率和综合得分排序。${SITE_NOTICE}`}
  noindex={false}
/>
```

它渲染 `<title>`、`<meta name="description">`、`<link rel="canonical">`、`og:title/og:description/og:type`、`<meta name="robots" content="noindex,follow">`（按需）。

**每页的 noindex 清单**（必须）：
`/me`、`/submit`、`/login`、`/register`、`/admin`、`/notifications`、`/compare`（对比页是个性化参数，索引价值低且会产出无限 URL）。

**落点 2：服务端注入（否则上面全白做）。**

`server/src/static.ts:25` 对任意路径都返回同一个 `index.html`；爬虫和社交卡片拿到的是空壳 HTML，`<title>` 永远是「什么值得蹬」（`web/index.html:6`）。两条路：

- **推荐：路径级别的 meta 注入。** 在 `index.html` 里放占位注释（`<!--META-->`），`mountWeb` 的 fallback 分支读一次 `index.html` 缓存字符串，按 `pathname` 匹配一张「静态路由 → title/description」表，替换后返回。成本约 60 行，不需要预渲染，也不影响现有构建。
- 备选：构建期预渲染（vite-plugin-prerender 之类）静态路由。收益更大（首屏内容也进 HTML），但要动构建链，风险高。

**落点 3：`/robots.txt` 与 `/sitemap.xml`。**

现在这两个路径都会命中 SPA fallback，返回 `index.html`（`server/src/static.ts:25`），爬虫会拿到 HTML 而不是文本——这是明显的坏信号。需要在 `mountWeb` 之前注册两条真实路由：`robots.txt` 里 `Disallow: /me /submit /admin /notifications /compare`，`sitemap.xml` 动态列出已通过的站点与文章（数据都在，`getStations` / `getPosts` 翻页即可）。

**落点 4：软 404。** `/stations/不存在` 返回 200（见 1.5）。修法：`StationDetailPage` 拿到 404 时渲染 `NotFound` 并把 meta 设成 `noindex`；服务端逐步改成对已知前缀下的未知 slug 返回 404 状态码（需要查一次库，成本可接受）。

**落点 5：og:image。** 没有对象存储也没关系：用 `StationTile` / `PostCover` 的纯 CSS 封面在当前实现里无法截图成图片，所以 og:image 统一用 `/favicon.svg` 转一张 1200×630 的静态图（构建期生成一次即可），按 `kind` 出 2~3 张（站点 / 文章 / 默认）。不要为了 og 图引入图片服务。

## 3. 关键流程设计

### 3.1 用户改一篇已通过的文章

```text
[文章详情页 /posts/:id]
  └ 标题下方操作区：作者可见 [编辑]
        ↓ 点击
[/submit?edit=<id>]
  └ 表单预填 title/summary/body/station/model，kind 锁定显示为 tag 不显示选择器
  └ 页头副文案：「修改要重新审核，审核期间线上仍是上一版」
        ↓ 修改后点「提交修改」
  ┌─ 校验失败 → 字段级 aria-invalid + 错误文案 + 焦点移到第一个错误字段
  └─ 成功
[回到 /posts/:id]
  └ 顶部 warn 条：「已提交修改，正在审核。线上仍是上一版，其他人看到的也是上一版。」
  └ 操作区：「编辑」变 disabled（有一版在审），新增「撤销修改」
  └ 列表卡（信息流 / 我的分享）tag：「修改待审」
        ↓ 审核通过
  └ 详情页 warn 条消失；通知：「你对《X》的修改已通过」
        ↓ 审核驳回
  └ warn 条变红：「修改未通过，线上仍是上一版」+ 驳回原因
  └ 操作区：「编辑」恢复可点，「撤销修改」消失（已经没有待审版本）
        ↓ 作者点「撤销修改」（在审核中时）
  └ 二次确认：「撤销后修改不会保存，线上版本不受影响。」
  └ 成功后 warn 条消失，恢复成普通已通过文章
```

**审核态呈现的三条铁律**：

1. 任何时刻，页面必须能回答「别人现在看到的是哪一版」。
2. 「待审」永远不能出现在公共列表里给别人看（`PostCard.tsx:30-31` 的 tag 现在对所有人渲染，依赖服务端只返回自己的待审稿——这个依赖是对的，但前端也应只在 `author.handle === me.handle` 时渲染，否则将来某个接口漏过滤就会直接泄露）。
3. 撤销必须存在。只能提交、不能撤回的审核流程，在第一次被驳回时就会逼用户重写一遍。

### 3.2 用户删自己的评论

```text
[评论区 /posts/:id #comments]
  └ 自己的评论 … 菜单 → [删除]
        ↓
  ┌─ 该评论没有回复
  │   确认框：「删除这条评论？删除后不可恢复。」
  │     [删除]（红底/实心） [取消]
  └─ 该评论有 2 条回复
      确认框：
```

## 4. 头像方案的交互取舍

**先看现状（这是最容易被忽略的一点）**：`User` 类型里已经有 `avatar: string`（`shared/src/domain.ts:37`），`Author` 继承了它（`domain.ts:54`），接口一直在返回这个字段——但前端 `<Avatar>` **完全没用它**，只按昵称做哈希取色 + 取首字（`visuals.tsx:40-60`）；首页用户卡的 `.user-avatar` 甚至是一张固定的鲸鱼图（`home.css:120-125`）。也就是说：**字段已经付过成本了，功能是零。** 这决定了下文的推荐方向——在已有字段上做低成本编码，而不是新造一套上传链路。

| 方案 | 交互体验 | 实现复杂度 | 关键约束 | 结论 |
|---|---|---|---|---|
| **A. 纯首字母色块**（现状） | 零操作，永不变更；同名不同人靠颜色区分；中文昵称取首字，视觉上尚可（`glyphOf`，`visuals.tsx:48`） | 已完成 | 用户无法自选；「我的头像」= 我改昵称，反直觉 | 保底，不作为最终方案 |
| **B. 外链 URL**（用户填一个图片地址） | 最「自由」，但要用户会拿到一个可公开访问的图片直链 | 低（前端 `<img src>` + 一段校验） | **会被 CSP 拦掉**：`server/src/static.ts:14` 是 `img-src 'self' data:`。要放开就得允许任意外站图片 → 隐私（第三方 IP 泄露、追踪像素）、大量 404、慢图、被墙域名 | **否决** |
| **C. 本地文件上传** | 体验最好（就是「换头像」） | **高**：需要 multipart 或 base64 接口、尺寸/类型校验、缩略图生成、垃圾内容审核，以及**存储** | 没有对象存储。只能把图存进 SQLite 的 BLOB 或 data URL：一张 64×64 WebP 约 3~6KB，但 `Author` 会随**每条评论、每篇文章、每条通知**一起返回（`domain.ts:54`）；评论每页 20 条（`Comments.tsx:53`）× 5KB ≈ 100KB 纯头像开销，还不能走 CDN 缓存。另外每张上传图都是一次 UGC 审核负担 | **否决（本阶段）** |
| **D. 预设图标集**（12 个内置 SVG/印章，选一个） | 一次点击、立即预览；视觉可控，和站点的印章/纸感语言一致（`VENDOR_ART` 就是这套做法，`visuals.tsx:19-36`） | **低**：`avatar = 'preset:crane'` 一个字符串；前端查表；`<Avatar>` 里加一个分支；无新接口、无存储、无审核 | 选择自由度有限；需要一次性画 12 个图标（可以先用 8 个） | **推荐** |

### 推荐方案：D + A 兜底

```
avatar 字段的取值约定：
  ''                      → 用昵称首字色块（现状行为，老用户不变）
  'preset:<key>'          → 内置预设图标
  'https://...'           → 本阶段不写库；即使历史数据里有，<Avatar> 也只当它不存在
```

**交互细节**：

1. 落点在 `Settings` 表单（见 2.9），一个 `role="radiogroup"` 的 8~12 格网格，每格是 40px 的图标 + `aria-label`（如「印章·红」）。选中项用 `aria-checked` + 现有 `.chip[aria-pressed='true']` 的高亮样式（`pages.css:28`）。
2. 第一格是「用昵称首字」，选它就等于清空 `avatar`——这样「我不想选」也有出路。
3. 不提供「随机」按钮：随机结果不可预期，用户会反复点，产生无意义写入。
4. 预览即时（本地 state），保存跟随表单（`Me.tsx:142` 的「保存」）。
5. **不变的部分**：`<Avatar>` 保持 `aria-hidden="true"`（`visuals.tsx:56`）。头像对读屏用户没有信息量（昵称就在旁边），把它变成「有意义的图片」反而会让每条评论多播报一次。头像**选择器**才是需要 `role="radio"` 和键盘可达的那一处。

**如果将来一定要上传**：最低成本路径是「由服务端把图缩到 64×64 WebP、存成 data URL、写入 `users.avatar`，并在所有列表接口里把 `Author.avatar` 换成 `avatarKey`（一个短哈希），图片另开 `GET /avatars/:key` 路由直接从 SQLite 读」——这样列表响应不带二进制，也能加 `Cache-Control: public, max-age=...`。**但在有对象存储之前，不要做。**

## 5. 移动端与可达性

### 5.1 断点与现有约束（新功能必须遵守）

- 断点只有两档：**1040px**（`home.css:278`、`chrome.css:87`）和 **760px**（`chrome.css:93`、`home.css:287`、`pages.css:201`）。新组件不要引入第三档，否则维护成本翻倍。
- `.container` 是 `min(1200px, 100% - 2*10px)`（`base.css:69`），移动端可用宽度 = 视口 − 20px。
- 触摸目标：现有 `.btn-small` 只有 `min-height: 28px`（`base.css:100`），移动端 `.post-side .btn` 34px（`home.css:352`）。**新增的「⋯」菜单、举报入口、对比勾选，触摸区必须 ≥44×44**——用透明 padding 扩大，不要改视觉尺寸（否则 PC 端按钮会突然变大）。
- 动效：`prefers-reduced-motion` 已有统一兜底（`base.css:187-195`），新动画不要自己写 `!important`。
- z-index 现有三档：`--z-flyout: 20`、`--z-nav: 30`、`--z-toast: 50`（`base.css:30-32`）。新增需要两个：`--z-compare-bar: 40`（在导航之上、弹窗之下）和 `--z-modal: 60`。**注意 toast 是 50，比 modal 低**——如果 modal 打开时出错要弹 toast，会被盖住。建议把 `--z-toast` 提到 70，标注「toast 永远在最上层」。

### 5.2 焦点管理（新功能的硬要求）

现有代码里**没有任何一处做过焦点管理**，所以新功能要立规矩，而不是沿用：

1. **弹窗（举报 / 删除确认 / 注销）**：
   - 用原生 `<dialog>` + `showModal()`，或自己实现时必须：`role="dialog"`、`aria-modal="true"`、`aria-labelledby` 指向标题、`aria-describedby` 指向正文。
   - 打开时焦点进「第一个可操作元素」；对**破坏性**弹窗，焦点要放在**取消**上（不是「删除」）。
   - Tab / Shift+Tab 循环在弹窗内，背景内容 `inert`（`BannerCarousel.tsx:18` 已经在用 `inert`，有先例）。
   - Esc 关闭；关闭后焦点**回到触发按钮**——不是回到 `body`。现在的 `DropMenu` 只做了 Esc 关闭（`Layout.tsx:107-118`），焦点掉到 `body`，键盘用户会丢失位置。
2. **下拉菜单（`DropMenu`，`Layout.tsx:103-128`）需要顺手修**：
   - `aria-haspopup="true"` 应为 `"menu"`（`Layout.tsx:122`）。
   - 菜单项应在 `role="menu"` 容器里，`↑`/`↓` 在项间移动、`Esc` 关闭并回焦。
   - 悬停会打开（`chrome.css:63-66`），但 `aria-expanded` 仍是 `false`（`Layout.tsx:122` 的 state 没被 hover 改变）——屏幕阅读器读到的状态和实际不一致。修法二选一：加 `onMouseEnter/onMouseLeave` 同步 state，或在 `@media (pointer: fine)` 里去掉 hover 打开、只保留点击。**推荐后者**，行为更确定。
   - 弹层常驻 DOM（`.share-popup { display: none }`，`chrome.css:56`），关闭时里面的链接仍可能被读到。要么条件渲染，要么加 `inert`。
3. **路由切换后的焦点**：`Layout.tsx:183-185` 在 pathname 变化时 `window.scrollTo(0,0)`，但没有把焦点移到 `<h1>` 或 `<main>`。SPA 里这会导致读屏用户不知道页面变了。建议：给 `<main id="main" tabIndex={-1}>`，路由变化后 `document.getElementById('main')?.focus()`，并配一个 `sr-only` 的 `<h1>`（首页已有，`Home.tsx:70`）。
4. **skip link**：`Layout.tsx:188` 之前加 `<a className="skip-link" href="#main">跳到主内容</a>`，样式为聚焦时左上角浮出。这是本仓库唯一完全没有的可达性基建。

### 5.3 键盘操作

- 「⋯」菜单必须是 `<button>`（不是 `<div onClick>`），`Enter`/`Space` 都触发。
- 评论删除后，列表**不要重排到顶部**；焦点落点见 3.2。
- 对比勾选框用原生 `checkbox`（可以视觉隐藏 + `aria-pressed` 按钮），支持空格切换。
- 站点对比浮条里的 `×` 移除按钮，`aria-label` 要带站名：「从对比中移除 A」，不要只写「移除」——浮条里有 3 个同名按钮。
- 头像选择网格：方向键左右移动（radiogroup 的标准行为），或在 `role="group"` 里用普通 Tab 序列（更简单、也不违规）。**选简单的那个**。

### 5.4 错误提示与 `aria-invalid`

现有两处半成品，新功能必须补齐：

- `Comments.tsx:44`：`.form-error` 没有 `role="alert"`，也没和 `textarea` 建立 `aria-describedby` 关联；`textarea`（`Comments.tsx:39-42`）没有 `aria-invalid`。
- `Submit.tsx:242-248`、`Submit.tsx:277`：有 `aria-invalid`，但错误 `<p className="form-error">` 没有 `id`，输入框也没有 `aria-describedby` → 屏幕阅读器只听到「无效」，听不到原因。

**统一规范（新表单照这个做）**：

```tsx
<input
  id="report-detail"
  aria-invalid={Boolean(error)}
  aria-describedby={error ? 'report-detail-error' : undefined}
/>
{error && <p id="report-detail-error" className="form-error" role="alert">{error}</p>}
```

服务端错误（`role="alert"`，全局一条）与字段错误（字段级 `id`）必须分开，不能都塞进 `form-error` 一个通道。

### 5.5 颜色与字号

- `.hint` 用的是 `--text-3: #85807b`（`base.css:9`、`75`），白底对比度约 4.0:1，**不到 12px 文字的 4.5:1 要求**。所以：**「审核中」「修改待审」「已举报」这类状态信息不能用 `.hint` 呈现**，要用 `.tag`（`base.css:106-117`，其中 `tag-warn` 的 `#9a5b06` on `#fff1d9` 是达标的）。
- 破坏性按钮不要只靠颜色区分。删除/注销按钮除了红色，还要有文字（「删除」「注销账号…」）——现在 `.btn-ghost:hover` 就会变红（`base.css:99`），单靠颜色没有信息量。

## 6. 空态设计（重点）

### 6.1 前提：生产环境就是空的

- `SITE_MODE=production` 时「站点、文章、用户、横幅一律为空，必须来自真实投稿或飞书同步」（`README.md:180`）。演示模式才有 12 个虚构站、48 篇文章。
- 线上真实数据是「13 个站点、49 篇文章、19 条投稿」（`README.md:347`）——注意其中大部分是演示站；**真实投稿只有 1 篇**。
- 所以下面每一页的空态都不是边缘情况，而是**首次访问者的主路径**。

### 6.2 现有空态的四类问题

1. **分不清「全空」和「筛选无匹配」。**
`Stations.tsx:70` 的 `empty={<Empty title="没有符合条件的中转站" />}` 在「库里一个站都没有」时也显示「没有符合条件的」——用户在筛一个不存在的集合，会把「这站是坏的」当成第一印象。`Models.tsx:54`、`Search.tsx:18` 同样。
2. **完全空缺。**
`RankingBoard.tsx:91-96` 没有传 `empty`，且 `children` 不读数组长度——数据为空时渲染 `<ol className="rank-grid">` 里什么都没有，页面上留下一个 52px 标题行 + 16px padding 的白块（`home.css:177`）。首页排行榜是最显眼的模块，它空着比任何一句话都更像故障。
3. **文案是占位符。**
`AsyncView.tsx:13-19` 的默认 `Empty` 是「这里还没有内容」，`Feed.tsx:58` 没传 empty，于是 社区 / 评测 / 首页信息流 三处都可能是这七个字。它没有告诉用户「为什么空」「可以做什么」。
4. **空态没有动作，或者动作指错地方。**
`Feed.tsx:111` 的 `action={{ to: '/submit', label: '推荐一个' }}` 是好的，但它落到 `/submit` 的默认 kind（`Submit.tsx:34` 默认 `deal`）= 发爆料，不是推荐站点。

**通用规则**：每个空态必须回答三件事——**这里是什么**（一句话说明这个模块的用途）、**为什么现在没有**（新站 / 还没人投 / 筛选条件太窄）、**我能做什么**（1 个主按钮 + 1 个次链接，主按钮必须真的打开对应的表单）。

### 6.4 两个实现要点

1. **`Empty` 组件需要扩展**（`AsyncView.tsx:13-20`）：现在只支持 `{ title, action: { to, label } }`。需要加 `hint?: string`（说明文案）和 `action?: { to?, href?, onClick?, label }`（支持打开弹窗/直接调接口，比如「去签到」是写操作，不是跳转）。改动很小，但 20 多处空态都要靠它。
2. **区分「全空」与「筛选空」**：给列表页一个 `total === 0 && !hasFilter` 的判定，`Stations.tsx` 的 `total` 在 `usePaged` 的 `first.data.total` 里已经拿得到（`hooks.ts:88` 用到过）。判定为「全空」时用引导型空态，否则用「清除筛选」型。

### 6.5 一个反例，不要学

`Home.tsx:53` 对空 Banner 的处理是「整块不渲染」，注释写得很清楚（「留着 16:10 的空框配一句『这里还没有内容』，首屏看起来像坏了」）。这是正确判断。但 `RankingBoard` 没有做同样的事（`RankingBoard.tsx:91-96`）——**同一类问题，一个修了，一个没修**。原因可能是排行榜的骨架屏写得太好（`rank-placeholder`，`home.css:178`），让人以为空的时候也会显示占位块；实际上骨架只在 `data === undefined` 时出现（`AsyncView.tsx:40`），`data` 为空数组时走的是 children 分支。这是本项目最容易复制的一个错误。

## 7. 文案规范

风格基线（来自现有代码，必须一致）：**直白、不客气、说清后果、不用感叹号、不用「哦」「啦」、不装作有人情味的客服**。示例参照 `PostDetail.tsx:23-24`（「审核中，目前只有你自己看得到」）、`Auth.tsx:127`（「暂不支持找回密码，请妥善保存」）、`AgentTokens.tsx:69`（「明文仅显示一次，请立即保存」）、`NotFound.tsx:9`（「这条路蹬不通，换个方向吧」——这里唯一的例外，只有 404 允许一个谐音梗）。

### 7.1 按钮文案

| 场景 | 文案 | 不要用 |
|---|---|---|
| 保存资料 / 头像 | 保存 | 确认修改、提交 |
| 提交新投稿 | 提交审核 | 发布、立即发布 |
| 提交修改 | 提交修改 | 更新文章（会让人以为立即生效） |
| 撤销待审修改 | 撤销修改 | 撤回、取消提交 |
| 删除文章 | 删除文章 | 删除、移除 |
| 删除评论 | 删除评论 | 删除 |
| 举报 | 举报 | 投诉（投诉暗示有客服流程） |
| 提交举报 | 提交举报 | 确定 |
| 兑换 | 兑换 | 立即兑换（不要催） |
| 注销 | 注销账号… | 删除账号（账号不是"文件"） |
| 对比 | 对比 | 开始对比 |
| 通知 | 全部标为已读 | 清空（不是删除） |
| 确认删除弹窗 | 删除 | 确定、是 |
| 取消 | 取消 | 关闭（弹窗里「关闭」和「取消」语义不同） |

规则：
- 破坏性按钮**必须带宾语**（「删除评论」而不是「删除」），因为在弹窗标题之外，按钮本身常被读屏单独播报。
- 带省略号（「注销账号…」）表示「还会再问一次」；不带表示「立即生效」。全站统一用这个约定。

### 7.2 确认文案（统一模板）

**结构**：`标题（问句，≤15 字）` + `正文（后果，逐条，≤3 条）` + `是否可撤销（一句话）`。

**删除评论（有回复）**
> 删除这条评论？
> 删除后这条评论不再显示，但下面 2 条回复会保留，仍然能被看到。
> 删除不可撤销。

**删除文章**
> 删除《标题…》？
> 评论、投票和收藏会一起消失。已通过的投稿可以从「我的投稿」里看到删除记录。
> 删除不可撤销。

**注销账号**（见 3.6 全文）

**撤销修改**
> 撤销这次修改？
> 修改内容不会保存，线上版本不受影响。

**吊销 Agent 凭证**（这是现有缺口，借这次一起补，`AgentTokens.tsx:91`）
> 吊销凭证「<名称>」？
> 使用这个凭证的程序会立刻失败。已提交的内容不受影响。
> 吊销不可撤销，需要重新生成一个新凭证。

### 7.3 错误文案

原则：**谁的问题、怎么办、要不要重试**。服务端文案已经比较到位（如 `format.ts`、`api.ts:51-61`），前端补齐时不要覆盖成「操作失败」。

| 场景 | 文案 |
|---|---|
| 网络/超时 | 请求超时，请检查网络后重试（已有，`api.ts:51`） |
| 未登录写操作 | 登录后才能<动作>。→ 不要只说「请先登录」 |
| 表单必填 | 请填写标题（已有，`Submit.tsx:24`） |
| 举报未选原因 | 请选择一个举报原因 |
| 举报太频繁 | 举报太频繁了，N 分钟后再试 |
| 余额不足 | 还差 N Token。签到每天 +10，去签到 |
| 删除失败 | 删除失败：<服务端原因>。刷新后重试 |
| 权限不足（改别人的文章） | 只有作者能编辑这篇文章 |
| 文章已在审核中 | 这条修改正在审核，审核完才能再改 |
| 注销密码错 | 密码不对 |
| 注销确认词错 | 请输入「注销」两个字 |
| 空结果（搜索） | 没有找到与"q"相关的内容。换个说法，或者直接看中转站库 |

**不要写的三种错误**：「操作失败，请稍后再试」（什么都没说）、「系统繁忙」（用户会以为被限流）、「出错了」（等于没说）。

|---|---|---|

## 8. 现有交互问题清单（含新功能会踩的坑）

按「该不该在下一版就修」排序。

### P0（会让用户以为功能坏了）

1. **排行榜无空态**（`RankingBoard.tsx:91-96`）。首页和 `/rank` 在最显眼的模块里渲染白块。修法：传 `isEmpty={(d) => d.items.length === 0}` + 引导型空态（见 6.3）。
2. **投稿成功后落到错误的标签页**（`Submit.tsx:70`、`Submit.tsx:110` 跳 `/me?tab=posts`，但补录模型/推荐新站的结果在 `submissions` 标签，`Me.tsx:21`）。用户刚提交完，看到的是「还没有分享」，唯一合理的推断是「提交失败了」，于是重复提交 → 撞上限流（`docs/spec.md`：投稿每小时 10 篇）。两处都改成 `navigate('/me?tab=submissions')`。
3. **Agent 凭证吊销零确认**（`AgentTokens.tsx:91` → `37-50`）。全站唯一不可逆的写操作，点一下就生效。这是新功能（删文章/删评论/注销）的模板，必须先立对。
4. **空态把「全空」说成「筛选无匹配」**（`Stations.tsx:70`、`Models.tsx:54`、`Search.tsx:18`）。见 6.3。

### P1（会让用户多走几步，或产生误解）

5. **补录模型 / 推荐新站提交后 `submitting` 不复位**（`Submit.tsx:71-74`、`111-114`：成功分支里 `setSubmitting(true)` 后不 `setSubmitting(false)`）。正常流程会跳走所以看不出来，但任何跳转失败（比如路由异常）都会让按钮永远停在「提交中…」。
6. **`PostDetail` 不显示驳回理由**，而 `PostCard.tsx:39-41` 显示。作者从「我的分享」点进详情，理由就消失了——详情页才是他会反复看的地方。补一行。
7. **空态的「推荐一个」指向错误的 kind**（`Feed.tsx:111`、`UserCard.tsx:66` 的 `/submit`）。应带 `?kind=station` / `?kind=review`。
8. **`DropMenu` 的 `aria-expanded` 与 hover 打开不一致**（`chrome.css:63-66` vs `Layout.tsx:122`），且 `aria-haspopup="true"` 应为 `"menu"`。
9. **`Feed` 的「最新 / 最热」用 `text-toggle`（`aria-pressed`），厂商筛选用 `select`，类型用 `segmented`（`aria-pressed`），排序在站点页用 `segmented`**——四种筛选控件表达同一类「选择」。新功能（对比页、通知页的 tab）建议统一到 `.tabs` + `role="tab"`（切视图）与 `.chip` + `aria-pressed`（切筛选）两种。
10. **`Comments` 没有取消回复的出口**：点「回复」（`Comments.tsx:97`）后弹出表单，只有提交才会 `setReplyTo(undefined)`（`Comments.tsx:71`）。不想回复了只能刷新页面。加一个「取消」。

### P2（长期债，会被新功能放大）

11. **`role="tablist"` 只做了一半**（`Me.tsx:221-225`、`RankingBoard.tsx:79-88`、`Admin.tsx:352-366`）：有 `role="tab"` 和 `aria-selected`，缺 `aria-controls`、`id`、`role="tabpanel"`、方向键切换。新加的 tab（我的 Token / 通知）不要复制这个半成品，要么补全，要么降级成普通链接组（`.tabs` 样式 + `<Link>`，最简单且不违规）。
12. **全站没有 skip link、`<main>` 无 id**（`Layout.tsx:191`）。
13. **详情页没有面包屑**，站点详情页无法回到列表（`Stations.tsx:95-105`）。
14. **所有 `<Empty>` 只有一行标题**（`AsyncView.tsx:13-20`），没有说明文案字段——这是第 6 节全部改动的前置阻塞项，应最先改。
15. **软 404**：任意不存在的路径返回 200 + 404 页面（`server/src/static.ts:25`），影响 SEO 和「这条链接到底失效没有」的判断。
16. **`FavoriteButton` 的 `aria-label` 恒为「收藏」**（`FavoriteButton.tsx:38`），已收藏时读屏仍播报「收藏」，应随状态变成「取消收藏」；且缺少数量语义（只播报一个数字）。新加的「关注」按钮直接照抄会传染这个错误。
