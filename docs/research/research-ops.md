## 1. 合规与法律风险

先给一个贯穿全篇的判断，它决定了后面每一条的等级：

> **平台从「中立存储」变成「内容发布者」，避风港就消失了一半。**
> 《民法典》第 1194–1197 条的免责前提是「网络服务提供者接到通知后及时采取必要措施」——即内容由用户提供、平台只做被动处置。而这个产品正在增加的三类东西：**平台自己生成的榜单/对比结论**、**付费或积分换来的优先展示**、**关注/通知驱动的推荐流**，性质上都属于平台自己的陈述。一旦这三者里任何一个成立，平台对该处的信息真实性负直接责任，不能再靠「用户投稿」脱责。所以第 2 节的数据诚信约束在本项目里**不是产品调性，而是责任分配条款**。

### 1.1 名誉权 / 商业诋毁：用户写差评怎么办

**现状**
- 站点是商业服务主体，点评直接指向其经营。现有内容里已经有攻击性表达的口子：`server/src/seed.ts:41`（「别只问能不能用，先问怎么退」）、`seed.ts:42`（质疑模型真伪）虽是演示数据，但示范了「跑路 / 假模型 / 骗钱」这类事实指控是社区预期写法。
- 评论正文字数上限 2000（`server/src/app.ts:857`），正文上限 10 万字（`app.ts:771`），足以写下完整的「我被骗了 3000 元」叙事。
- 处置手段只有两档：`withdrawPost` 软删除（`server/src/moderation.ts:58-68`）与 `setCommentHidden`（`moderation.ts:98-102`）。**没有**「部分修改」「加注说明」「要求作者补充证据」这类中间态，也没有任何对外的申诉/反通知入口。
- 平台侧的风险放大器已经存在：`/business` 页写着「站点入驻与资料更新」「评测与测试协作」（`web/src/pages/Business.tsx`），即平台与**被点评对象**有商业往来。

**具体后果**
1. 中转站经营者发律师函时，标准打法是「你平台既做导购又收合作，还放任不实差评，属于《反不正当竞争法》第 11 条的商业诋毁帮助方 / 你自己的虚假宣传」。平台唯一能拿出的抗辩是「已及时处置」，而现在**没有处置留痕**（见 1.6），举证直接失败。
2. 反向风险同样真实：平台如果因为商家一封函就删差评，就构成对消费者的信息操纵，且在 `/business` 页「榜单和评价不接受付费改动」的自我承诺下构成虚假陈述。
3. 演示数据混在生产库里时（B3），「虚构·XX 站跑路」这种内容在页面上和真实站并排，法律上属于**平台自己**发布的虚假信息，不是用户投稿。

**风险等级：高**

**建议措施**
- 分层而不是二分：新建 `dispute`（争议）中间态，让被点评方可提交「事实性异议 + 证据」，平台只做三件事之一——要求作者补证、加注「涉事方对该内容有异议」、或按结论下架。加注是成本最低、法律上最有效的一档，应作为默认动作。
- 社区规范里明确禁止无依据的**事实性断言**（跑路、诈骗、卷款、假 API），允许主观评价（慢、贵、客服差）。这条要写进投稿表单的提示文案，而不只是条款页——审核时的判断标准要和用户看到的提示一致。
- 对「涉刑/涉诈」类指控设置强制人工复核，不得走批量通过（`app.ts:456-502` 的 batch-review 必须排除此类，否则一键通过就是一键放大）。
- 涉事方异议入口必须挂在站点详情页，而不是只留一个邮箱；`Business.tsx` 的「联系方式待配置」在开放任何点评流量之前必须落地。

### 1.2 用户生成内容的存储与删除义务

**现状**
- 内容存在两处：`entities`（JSON，软删除靠 `removedAt`，`server/src/database.ts:22-27`）与 `submissions`（原始 payload 快照，`database.ts:131-147`）。
- 软删除是「数据留着」，**没有任何物理删除路径**：`moderation.ts:58-75` 只改标记，`README.md:91` 明确「正文、报价一直是原样留着的」。
- 投稿被拒后 payload 永久保留（`submissions.ts:282-284` 无条件插入），包括正文、URL、IP。
- 备份每天 1 次、保留 14 份（`deploy/zhidedeng-docker-backup.sh` 的 `keep=${BACKUP_KEEP:-14}`），备份里含被删内容的旧版本。

**具体后果**
- 「删除」在当前架构里是**不可兑现的承诺**。一旦对用户或监管说「已删除」，而库里、备份里都还在，就是虚假陈述。
- 新增「文章编辑/删除、评论删除、账号注销」三个功能后，用户会**第一次**产生「我要这东西消失」的真实诉求；现在没有任何机制能回答「多久真删」「备份里的怎么办」。
- 评论的删除还受外键约束：`comments.parentId REFERENCES comments(id)`（`database.ts:50`）且 `PRAGMA foreign_keys = ON`（`server/src/node-app.ts:22`）——**物理删除父评论会直接失败或被 RESTRICT 拦下**，实现者大概率会退回「只置 hidden」，然后对外仍宣称「已删除」。这是最容易发生的实现级违规。

**风险等级：高**

**建议措施**
- 定义三级语义并写进用户协议：①**下架**（`removedAt`/`hidden`，前台不可见，数据留档，可恢复）；②**删除**（用户主动，N 天后物理清除，含 payload 与关联行）；③**匿名化**（注销时保留内容但抹掉身份，见 1.5）。
- 评论删除一律走软删除 + 前台占位「该评论已删除」，父评论删除时子回复一并下架（复用现有 `COMMENT_VISIBLE` 的子查询逻辑，`server/src/service.ts:60`）。
- 投稿被拒的 payload 应设保留期（建议 90 天）后清空正文、只留 hash 与元数据——拒绝理由需要留档，但被拒的正文没有继续保存的必要。
- 明确备份的例外：告知「备份最多 14 天后自然轮转清除」，这是行业可接受表述，但不能不说。

### 1.3 个人信息：`submissions.ip` 与 `audit` 逻辑是否过度收集

**现状**
- `submissions.ip` 为 `TEXT NOT NULL`（`database.ts:142`），**没有保留期、没有清理任务**，写入点覆盖全部渠道：站内投稿 `app.ts:782-784`、`app.ts:795-797`、`app.ts:840-842`，Agent 提交 `server/src/agent-api.ts:222`，飞书批次 `app.ts:370`。
- 管理端返回的 `SubmissionRecord`（`shared/src/api.ts:23-36`）**不含 ip 字段**——这点做对了，IP 没有随列表泄漏。
- 但 `payload` 原样返回，而 `README.md:359` 自己承认：站点 URL 的路径里可能带邀请码或令牌，「靠人工审核把关」。加上新功能要存的「举报理由」「异议证据」，`submissions.payload` 会变成事实上的**自由文本 PII 收集池**。
- 另一处隐性 PII 是 `rate_limits(bucket, key, at)`（`database.ts:110-114`）：键里含 `register:<ip>`、`login:<ip>`、`agentTokenIp:<ip>`（`app.ts:573`、`app.ts:616`、`app.ts:710`）。过期行「在写入时顺带清理」（`README.md:334`），**没有写入发生时永不清理**。
- 没有隐私政策，没有告知页，没有任何「为什么收集 IP」的说明（全仓库搜不到隐私/协议页）。

**具体后果**
- 《个人信息保护法》第 6 条要求最小必要、第 17 条要求告知。IP 属个人信息，收集本身有正当性（`README.md:334` 的限流与防刷），但「永不删除 + 无告知 + 无目的说明」三件套同时成立时，属于典型的可处罚形态。
- 《网络安全法》第 21 条要求网络日志留存不少于六个月——这是**留存的下限，不是无上限的许可**。正确做法是「安全日志 6 个月」，而不是「业务表里永远躺着 IP」。
- 新增举报/注销功能后，`submissions.ip` 的含义会从「投稿来源」扩展到「举报人来源」，一旦某次数据导出或后台截图流出，等于公开了「谁举报了谁」，这是最危险的组合（见 4.3）。

**风险等级：中（合规表象）／高（一旦叠加举报与注销）**

**建议措施**
- 拆分用途：限流/风控只用 `rate_limits`，到期即删；业务表只存**不可逆截断**后的 IP（建议 IPv4 保留 /24、IPv6 保留 /64，即 `normalizeIp` 现有粒度，`app.ts:124-148`），或直接只存一个 `ipHash`（加盐 HMAC，轮换密钥）。
- 定保留期：`submissions.ip` 90 天置 null；`rate_limits` 按窗口最大值清理（建议每日一次维护任务，别依赖「写入时顺带」）。
- 补最小告知：注册页一行 + 隐私政策页，说明收集 IP 用于防刷与安全审计、保留期限、不含定位用途。这是低成本项，但没有就不能对外解释。
- **举报人身份单独加密列**，不进 `payload`、不进管理列表默认返回（详见 4.3）。

### 1.4 举报机制：这不是产品功能，是法定义务

**现状：完全没有举报入口。** 全仓库无举报相关代码；`/business` 是唯一的外部联系方式页，且写着「联系方式待配置」（`web/src/pages/Business.tsx`）。用户遇到违法/侵权内容，唯一路径是去别的渠道找人——而运营是一个人兼职。

**具体后果**
1. **法律上不满足最低要求**。《互联网跟帖评论服务管理规定》要求跟帖评论服务提供者建立举报受理与处理机制、在显著位置公布举报方式并及时处理；《网络信息内容生态治理规定》要求设置便捷的举报入口并及时反馈。评论功能（`service.ts:805-817`）已经上线，等于已经在提供跟帖评论服务，却没有配套的举报与公示渠道——这是**已经存在的合规缺口**，不是新功能引入的。
2. **通知—删除规则无法运转**。《民法典》第 1195 条要求接到通知后「及时」转送并采取必要措施，第 1196 条要求转送反通知。没有举报入口、没有处理留痕、没有反通知路径，等于放弃避风港并保留全部责任。
3. **举报会成为删差评的武器**。中转站之间互相举报、商家举报差评，是这个品类里必然发生的事。如果「举报 → 自动下架」或「举报 → 优先审核」，平台就变成商业诋毁的执行端；如果举报完全不处理，就变成 1.1 的放任。两头都是责任。

**风险等级：高（必须做，且必须带流程一起做）**

**建议措施**
- 举报入口常驻在文章、评论、站点三处，且**必须能举报站点**（被点评对象是站点，不是文章）。
- 分类而非自由文本：`违法信息 / 侵权（名誉、著作权）/ 虚假信息（价格、指标）/ 垃圾广告 / 其他`。原因是只有分类才能分流到「24 小时必须处理」与「7 天处理」两档，一个人兼职才排得开（见 3.2）。
- 硬规则：**举报不触发自动下架，任何情况下都不。** 只入队。理由写进代码注释，防止后来者「优化」成自动下架。
- 反通知必须存在：下架时通知作者 + 给出申诉入口，申诉通过可恢复（复用 `restorePost`、`POST /api/admin/stations/:slug/restore`，`app.ts:428-433`）。
- 公布渠道：把 `/business` 的「联系方式待配置」换成真实可用的举报邮箱/表单，并写清处理时限。这一条是**上线任何 UGC 前的硬门槛**。

### 1.5 账号注销与数据删除义务

**现状**
- 明确不支持：`README.md:333`「不能注销账号」；`Me.tsx` 只有昵称/简介/改密码。
- 身份模型是 `accounts.handle` ↔ `users.handle` ↔ 内容里的 `authorHandle`（`database.ts:57-63`、`service.ts:164-170`）。**`handle` 同时是主键、是 URL 的一部分、是作者的唯一引用**。
- 没有任何墓碑/保留字机制来防止 `handle` 复用：注册只校验 `usernameKey` 唯一（`app.ts:578`、`app.ts:592`），删除后该键释放。

**具体后果**
1. **身份冒用**：注销 → 同名重新注册 → 新账号自动「继承」旧账号的全部历史文章、评论、达人榜位置与投票权重（因为 `authorHandle` 字符串相同，`service.ts:84` 的 `POST_AUTHOR` 就是按 `authorHandle` 匹配）。这是**高危越权**，比数据不删更严重。
2. **注销逃避封禁**：被禁用的账号（`setAccountDisabled`，`moderation.ts:78-96`）目前只是 `disabledAt` + 删会话 + 吊销凭证，注销后重新注册即可复活，且公开内容保留说明「封禁不删内容」，攻击者可以留着内容、换个身份继续。
3. **删除义务落不了地**：注销后要删什么？`accounts`、`sessions`、`agent_tokens` 可以删；`entities.user` 删了会让 `author()` 取不到值（`service.ts:167-169` 用的是非空断言，删掉会抛异常并 500，而不是优雅降级）——这会在注销功能上线第一天变成首页 500。
4. 备份与举报快照里的旧数据无法追溯清除（与 1.2 同源）。

**风险等级：高**

**建议措施**
- **`handle` 墓碑表**：注销时写入 `retired_handles(handle, retiredAt, reason)`，注册时先查此表，命中返回「该用户名不可用」。昵称同理（`normalizeNickname` 已有归一函数，`app.ts:588`，加一层保留即可）。
- 注销分两步、留冷静期（建议 7 天，可撤销），期间账号冻结不可登录；到期后执行。
- 注销时**必须**让 `author()` 对缺失用户优雅降级（返回「已注销用户」占位），而不是 `store.get('user', handle)!` 直接崩。这需要把 `service.ts:167` 的非空断言改成显式分支——**这条不修，注销功能不能上**。
- 内容处理给用户二选一：匿名化（保留文章与评论，作者显示「已注销」）或 全删（作者内容一并下架）。默认匿名化，因为全删会破坏他人评论的上下文。
- 封禁与注销解耦：被封禁账号不允许自助注销（或注销后仍保留 `disabledAt` 到墓碑表），否则封禁形同虚设。

### 1.6 主体资质与公示（当前 0，所有对外功能的前置）

**现状**：页脚只有「不构成消费建议」与「与本项目与什么值得买及任何模型厂商、中转站均无关联」（`web/src/components/Layout.tsx:166`）。**没有**运营主体名称、没有 ICP 备案号、没有公安备案号、没有隐私政策、没有用户协议、没有社区规范、没有举报渠道。

**具体后果**
- 点评商业服务 + 导购 + 潜在的商业合作（`Business.tsx`）＝《互联网信息服务管理办法》意义上的经营性服务，公网运营需 ICP 备案；未备案而对外提供信息服务，是可直接关停的形态。
- UGC + 评论 = 需要后台真实身份认证（《互联网用户账号信息管理规定》《互联网跟帖评论服务管理规定》）。现在只有用户名 + 密码，**没有手机号也没有邮箱**（`README.md:43`、`README.md:333` 明确「不要邮箱和手机号」）——这个产品形态本身与「后台实名」要求不兼容。这是需要提前决策的战略问题，不是实现细节：要么接入一个最小化的手机号验证（成本、PII 增加、与「不要手机号」的设计冲突），要么明确不做公网公开运营（保持内网/邀请制）。
- 广告可识别性：见 2.1 与 1.7。

**风险等级：高（阻断级）**

**建议措施**：把「域名 + 备案 + 主体信息公示 + 隐私政策 + 用户协议 + 社区规范 + 举报渠道」打成一个上线包，任何一项缺失都不开放 SEO 与公网注册。

### 1.7 Token 积分兑换：一旦换到「优先展示」就是付费排名

**现状**
- Token 目前只有两个来源：注册 120（`server/src/auth.ts:13`）、签到 10 + min(streak,7)（`service.ts:531`）。
- **没有任何消耗出口**，也不进任何排序。换句话说 Token 现在是一个纯装饰性的数字，没有经济含义。
- 排序逻辑全在服务端且与 Token 无关：站点 `score` 在 `uptime` 为 null 时短路为 null（`service.ts:243`）、榜单门槛 `MIN_OFFERS_FOR_RATE = 3`（`service.ts:64`）、模型榜 `stationCount + 1/lowestRate`（`service.ts:856-857`）。
- 平台已经公开承诺「榜单和评价不接受付费改动」（`web/src/pages/Business.tsx`）。

**具体后果**
- 若兑换「优先展示/置顶/加精」，则：① 与 `Business.tsx` 的承诺直接矛盾，构成对用户的虚假陈述；② 排序结果变成平台陈述，避风港失效（见本节开头）；③ 属《广告法》第 14 条与《互联网广告管理办法》要求显著标明「广告」的情形，且《电子商务法》第 40 条对竞价排名有明确标注要求；④ 中转站是付费方时，这就是导购返佣的变体，需要广告经营资质与发票链路。
- 更隐蔽的一种：兑换「曝光券」让**文章**进首页信息流。这同样是把 UGC 变成平台推荐位，且首页轮播（`BannerCarousel.tsx`）本来就有「Banner 是 AI 生成的插画」（`README.md:382`）这种非商业内容，混入付费内容后更难辨识。
- 若兑换的是**虚拟装饰**（徽章、头像框、称号），则风险极低，但也没有运营价值——见 3.4。

**风险等级：高（若兑换影响任何排序/曝光）／低（若只换装饰）**

**建议措施**
- 划定红线：Token **不得**影响 `score`、`lowestRate`、榜单 `rank`、信息流 `sort=hot`、搜索排序中的任何一个。任何兑换物都不得进入这些计算路径。
- 若确实要做商业化，走独立且明确标注的「推广位」：固定位置、固定样式、标「广告」、不进榜单、不参与任何算法排序，且不与「值/不值」并列展示。这条边界要写进代码（例如排序函数内注释 + 测试断言），因为它会被后来的产品需求反复冲击。
- 先给 Token 一个**非曝光类**出口：兑换「修改昵称冷却」「举报加急」「导出我的数据」这类，既消耗存量又不碰排序。

### 1.8 版权与分发授权（编辑、RSS、SEO 的直接后果）

**现状**：无用户协议，因此平台对用户正文只有「展示」这一默示许可，没有复制、改编、再分发的书面授权。而 RSS 与 sitemap 天然是**对外分发**。

**具体后果**
- RSS 输出全文＝把用户作品复制到第三方阅读器/聚合站，超出默示许可范围；作者主张侵权时，平台无法举证授权。
- 文章编辑功能引入第二个问题：编辑后的内容版本归属不清（是作者的还是编辑的？），且「编辑后指向外站」会让平台对改写后的内容承担发布者责任（见 4.1）。
- sitemap/OG 会把内容变成搜索引擎的持久副本，**删除后仍可从缓存与第三方索引访问**——这与 1.2 的删除承诺冲突，必须在协议里预先说明。

**风险等级：中**

**建议措施**
- 用户协议里给一条最小授权：非独占、免费、可用于站内展示与站外推广（含 RSS/搜索摘要/社交卡片），撤回时平台在合理期限内停止新的分发。
- RSS 默认输出**摘要 + 原文链接**，不输出全文；这也顺带降低被全文抓取后「删除无效」的问题。

### 2.1 Token 兑换「优先展示」是否等于花钱买排名

**是，等价，没有模糊空间。** 判定不看支付媒介是钱还是积分——积分可以靠签到无限获得（每天 1 次、`service.ts:526-538`），也可以靠多账号获得。一旦「积分 → 曝光」的兑换率存在，曝光位就有市场价格，就是排名交易。

三个具体后果：
1. **与既有承诺冲突**：`Business.tsx` 写「榜单和评价不接受付费改动」。这不是内部备忘，是对外承诺，改它需要公开说明，不能静默改代码。
2. **责任性质改变**：UGC 内容平台可以主张「用户写的」；一旦平台按积分分配曝光，该位置的排序就是平台自己的商业决策，需按广告规则标注，并对内容真实性负责（见 1.7）。
3. **数据诚信失守的具体形态**：被兑换提升的站点若 `uptime` 为 null，它在排序靠前的位置会显示「暂无」而不是 0 分——表面上没编数据，但**位置本身在暗示它是更好的选择**。这是「不编造指标」约束绕过不了的漏洞：指标没编，结论编了。

**结论**：可以做 Token 兑换，但兑换物不得影响任何排序或曝光；若要做商业化曝光，必须另建「广告位」概念并标注，且 `docs/spec.md` 需新增一条硬约束：「任何积分/付费机制不得进入 score、lowestRate、rank、hot 排序」。

### 2.2 SEO / sitemap / RSS / OG：当前最危险的组合（叠加 B3）

这是本次评审里我判定**风险最高**的功能，原因是它把 1.2、C1、C6 三个问题同时引爆，而且**不可撤回**。

具体后果：
1. **把 48 篇虚构文章与 12 个虚构站推给搜索引擎**。现在它们的「虚构」身份靠页面上的 `虚构·` 前缀与页脚 `SITE_NOTICE`（`web/src/format.ts:18`、`Layout.tsx:166`）。进入 sitemap 后，抓取快照、搜索结果摘要、第三方聚合站会**永久保留去掉声明的版本**。之后即使 `purge:demo` 清理干净，外部索引仍在。这是「演示数据必须标明」约束事实上的永久性突破。
2. **OG 卡片天然丢弃声明**。`web/index.html:7` 的 `description` 只写了「演示数据为虚构，群友提交未经核实」，**漏了 agent 来源**——而 `format.ts:18` 的 `SITE_NOTICE` 明确要求三类点齐（`spec.md:23`：「少写一类会让读者把它归到另外两类里」）。分享到微信/Telegram 时，用户看到的就是这张缺一类的卡片。这是现在就存在的漂移，加 OG 会把它固化到每一个外链预览里。
3. **RSS 会被当成事实来源引用**。评测类内容一旦可订阅，中转站商家会拿「什么值得蹬评为 0.6x 优质站」做宣传，而原文里「未经平台核实」的标注在引用中消失。平台无法控制二次传播，但可以控制**是否提供便捷的抓取通道**。
4. **站点对比页 + sitemap 是最坏组合**：对比页把多个站的数字排成表格，是搜索引擎最容易被抓成「结构化摘要」的形态，且表格里「暂无」在摘要里常被丢掉。
5. 反向问题：`/api/health` 未认证暴露 `mode` 与前端产物状态（`app.ts:302-316`、`README.md:371`），sitemap 上线后机器人会大量请求，日志噪音会让「真实访问」彻底不可观测。

**风险等级：高**

**建议措施（顺序不能颠倒）**
1. 先 `pnpm purge:demo --apply`（`README.md:186-193`），确认 `source='demo'` 行数为 0。
2. 再给 sitemap 加来源过滤：只收录 `source ∈ {user, submission, agent}` 且 `status='approved'` 且 `removedAt IS NULL`，并对 `submission`/`agent` 的来源页在 `<meta name="robots">` 上加说明性标注（不用 noindex，但要保证声明在首屏可见，不依赖页脚）。
3. OG/结构化描述必须包含完整三类来源声明，并把 `index.html:7` 的 `description` 与 `format.ts:18` 的 `SITE_NOTICE` 收敛到**同一个常量**（现在是两份手写文本，必然漂移）。
4. RSS 只输出摘要 + 链接，标题里带来源标签。
5. 在 SEO 上线前先确认 B1/B2（域名、HTTPS、反代）——现在没有域名、没有 TLS，sitemap 里的 URL 只能是 `http://172.16.81.4:8788/...`，这种 sitemap 提交给搜索引擎没有任何意义，只会暴露内网结构。

### 2.3 站点对比是否会放大未经核实的数据

**会，而且对比是「放大」的最佳载体。** 对比页的天然形态是一张数字表，而这张表里三类数据性质完全不同：

| 列 | 来源 | 现实 |
|---|---|---|
| 倍率 | 用户/Agent/飞书提交 + 人工审核 | 未经平台核实，可能过期（`quotedAt` 可为 null，`database.ts:35`） |
| 可用率 / 首 token 延迟 | **永远为 null**（`spec.md:20`、`submissions.ts:421`） | 对比表里全是「暂无」 |
| 综合得分 | `uptime` 为 null 时也为 null（`service.ts:243`） | 同样全空 |
| 值/不值 | 投票，可被多账号刷（`app.ts:848-853` 只限频不限账号） | 可操纵 |
| 演示站的行 | 虚构 | `虚构·` 前缀 + 页脚声明 |

具体后果：
1. **一列全空的可比表，会被读者读成「这家没数据＝不透明＝差」**。这在事实上把「没有实测数据」变成了负面评价——与 C3「不当 0 分也不编造」的**精神**冲突（虽然形式上没编造）。对比页必须显式说明「本站不采集实测指标，可用率/延迟一列恒为暂无」，否则就是用一个空列做了隐性排名。
2. **倍率跨口径不可比**，这是代码里反复强调的（`database.ts:32-35`、`service.ts` 的分组排序、`README.md:357`）。对比表如果只是把「最低倍率」一列并排，就把 4 种口径压成一个数字——比单站页面更容易误导，因为单站页至少先分组再排序。
3. **demo 站混入**：12 个虚构站有完整的 `uptime`/延迟（种子写入），而真实站全是 null。对比表放在一起，虚构站看起来是「数据最完整的优质站」。这是当前数据状态下**必然发生**的误读。
4. 对比 URL 可分享 → 分享出去的是一张脱离页脚声明的表（同 2.2 第 2 点）。

**风险等级：中高**

**建议措施**
- 对比页硬性规则：只允许对比**同口径**的倍率，按 `basis` 分组呈现，不提供跨口径的「最低价」行。
- `uptime` / 延迟列在全部对比对象均为 null 时**不显示该列**（而不是显示一列「暂无」），并附一行说明「本站不采集实测指标」。
- 对比页每一行必须带来源标签（`sourceLabel`，`web/src/format.ts:20-24`），不允许只在页脚声明。
- **默认排除 `source='demo'` 的站点**，若要包含需显式勾选。理由：对比表的目的是做选择，而虚构站不存在「选择」这回事。
- 不提供「综合推荐」「性价比排名」这类由对比派生的结论——那会把平台变成评价者。

### 2.4 文章编辑：直接冲击 C2（来源正文纯文本）与「审核后内容一致」

**现状**：内容来源决定渲染方式——`submission`/`agent` 来源按纯文本渲染，`user` 来源按 Markdown 渲染（`spec.md:19`、`web/src/pages/PostDetail.tsx:44`、`web/src/components/Markdown.tsx`）。审核通过后正文固化在 `entities` 里。

**具体后果**
1. **编辑即绕过审核**。`reviewPost` 对已物化文章是 `store.put('post', id, {...post, status})`（`moderation.ts:43`）——任何实现者复用这条路径做「保存编辑」，结果都是**已审核内容被直接替换且状态仍为 approved**。这条路径必须显式禁止。
2. **来源标签与渲染方式会脱钩**。一篇 `submission` 来源的文章如果允许作者编辑正文，它仍是 `source='submission'`，但内容已经是作者后来写的——「群友表单提交」的标签开始说谎。更糟的是若编辑时把渲染方式改成 Markdown，一篇按纯文本审核过的内容会突然变成可渲染 Markdown（含链接）。
3. **编辑后指向外站**是最常见的变现路径：先发一篇正常评测通过审核，两周后把「某站」的链接换成自己的返佣链接。当前 Markdown 渲染的链接是 `target="_blank" rel="noopener noreferrer"`（`Markdown.tsx:12`），**没有任何域名白名单**，外站链接可直接点击。
4. **评论区证据链断裂**：评论里说「原文写的是 X」，编辑后原文变成 Y，举报与争议处理失去事实基础（与 1.1 直接相关）。

**风险等级：高**

**建议措施**
- 编辑必须产生新版本并**重回 pending**：需要 `post_revisions` 表（`entities` 单条 JSON 存不下双版本），前台在审核期间继续显示旧版并标注「有修订待审」。
- 编辑不得修改 `source`、不得修改渲染方式、不得修改 `authorHandle`。
- 链接管控：正文中的外链统一加 `rel="nofollow ugc noopener"`，并在审核台展示「本次编辑新增/变更了 N 个外链」。若不打算做外链白名单，至少要让新增外链成为审核时的必看项。
- 若成本不允许做 revision 表，**降级方案是取消编辑，只保留「下架 + 重新投稿」**（见 6.2）。这是我认为更符合当前阶段的选择。

### 2.5 文章/评论删除：与 C5（下架拒绝 demo、保留 source）的一致性

**现状**：`withdrawPost` 拒绝 `source='demo'`（`moderation.ts:65`），`removeStation` 同样（`submissions.ts:641-647`）。这是刻意的：演示数据撤掉会让站点看起来像坏了。

**具体后果**
- 新增「作者自助删除」时，如果作者是 demo 用户（`demo-` 前缀，`seed.ts:34`），删除逻辑会撞上这条拒绝；实现者很可能直接在用户侧删除里跳过 demo 检查 → 演示数据可被删除 → 站点数量对不上、首页缺块，且 `purge:demo` 的幂等假设被破坏。
- 评论删除没有 demo 概念（`comments` 表无 source），所以「删除演示评论」永远成功——清理 demo 时会出现「文章删不掉但评论能删」的荒谬状态。

**风险等级：中**

**建议措施**：所有面向用户的删除/编辑入口，在服务端统一先过一道 `isDemoEntity` 守卫并返回明确错误（「演示内容不支持自助删除」）；这条守卫放在 `Service` 层而不是各路由，避免漏点。`purge:demo` 之前，用户侧删除功能建议直接关闭。

### 2.6 Token 兑换与 C7（不写绝对价格）

**风险点**：兑换如果引入「充值门槛折扣」「代金券」「满减」，就会在页面上出现绝对价格（元）。而 `rechargeThreshold` 已经是元（`spec.md:32`），是既有例外；再叠加兑换会把它从「信息」变成「交易」。

**等级：中。** 措施：兑换物永不涉及金额、永不与 `rechargeThreshold` 交互；倍率与金额的展示路径保持不变。

### 2.7 关注/通知是否会变成内容推荐从而强化不实信息

**会。** 这是本节里最容易被低估的一条，因为它的机制是「用户自己选的」——但实际效果是推荐系统：

1. **关注 → 动态流 → 事实上的推荐位**。用户关注一个被 Agent 提交、仅经一次人工审核的站点，之后该站点的任何报价更新都会推送给他。而报价更新走的是 upsert 物化（整包替换，`README.md:356`），**没有二次核实**。于是「关注」把一个待核实的数字变成了定向推送。
2. **通知的措辞就是平台陈述**。「XX 站倍率降到 0.4x」「你关注的站有新评测」这类文案是平台写的，不是用户写的。一旦数字是错的，这句话就是平台自己发布的虚假信息（同 1.1 开头的判断）。
3. **算法推荐合规**：一旦形成按关注关系分发的信息流，就落入《互联网信息服务算法推荐管理规定》的适用范围——需要说明推荐规则、提供关闭选项、不得诱导沉迷。一个人兼职运营做不了这些。
4. **负向强化**：`submissions.ip` 式的问题在这里变成社交图谱问题——关注关系是个人信息，公开「谁关注了谁」会暴露用户对特定中转站的兴趣，这在中转站可能涉灰的品类里是真实的隐私风险。

**风险等级：中高**

**建议措施**
- 不做「关注用户」，只做「订阅对象」（站点/模型/文章分类）。对象订阅没有社交图谱，没有粉丝数，没有互相骚扰。
- 通知只做三类且文案中性：「你订阅的站点资料被更新」「你的投稿有审核结果」「有人回复了你的评论」。**不做**「降价提醒」「值得买提醒」——那需要平台对价格真实性背书。
- 订阅更新通知必须带来源标签与「未经核实」，且不聚合、不排序、不做「本周精选」。
- 不做公开的订阅数/粉丝数展示（防刷 + 防画像）。

## 3. 运营可行性（前提：一个人兼职）

### 3.1 最硬的一条：SLA 不能按法定上限写

一个人兼职，意味着可承诺的处理能力约等于「每天 1 次、每次 30 分钟」。这决定了 SLA 只能写成分级的、且必须诚实：

| 类别 | 承诺时限 | 为什么 | 可行性 |
|---|---|---|---|
| 违法信息（涉黄赌毒、涉诈、明显违法） | 24 小时内下架 | 法定「及时」的实践下限，且这类内容一旦扩散责任最重 | **只有在不做人工初审的前提下不可行**。建议：该类内容先自动隐藏（保守），再人工复核——「误隐藏」可恢复，「晚隐藏」不可逆 |
| 侵权通知（名誉权/著作权，含证据） | 48 小时内转送 + 7 天内结论 | 《民法典》1195「及时」+ 1196 反通知需要时间窗 | 可行，但要求举报表单强制填证据，否则一律退回 |
| 虚假信息（价格/指标与页面不符） | 7 天内 | 需要核对第三方页面，成本最高 | 可行，但必须限流（见 4.3） |
| 垃圾广告/低质 | 14 天内或批量处理 | 无时效压力 | 可行 |
| 一般申诉/反通知 | 7 天内 | 与上面对称 | 可行 |

**关键设计选择**：SLA 写在**举报回执页**上（用户提交后立刻看到「我们承诺 X 天内答复」），而不是只写在条款里。写出来就要做到；做不到的档位不要写。现在没有任何回执机制，这是必须一起做的最小件。

### 3.2 审核台页签：会从 5 个变成 8 个，必须重构而不是叠加

现状 5 个页签（`web/src/pages/Admin.tsx:65`：`submissions | posts | published | removed | removedPosts`）。若举报、异议、注销申请各加一个页签，就是 8 个；再算上「编辑待审」就是 9 个。

**这在一个兼职运营手里是致命的**——不是因为页面难看，而是因为**页签数量直接等于「每次巡检要记得点几下」**。漏掉一个页签 = 一个类别的内容永远卡在队列里，而队列里卡着的东西是用户已经提交、以为会被处理的。

**建议的替代结构**：
- 只保留 **2 个一级视图**：`待我处理`（把所有需要人决策的东西合成一个按优先级排序的流：违法举报 > 侵权通知 > 待审投稿 > 编辑待审 > 注销申请）与 `已处理/可恢复`（下架文章、下架站点、已驳回）。
- 类型用筛选 chip 表达，不用页签。当前 `Admin.tsx` 的 5 个页签里有 2 个（`removed`、`removedPosts`）本质是「已处理」，可以合并。
- 每条卡片上直接显示「为什么它在这里」（来源、举报分类、SLA 剩余时间），让运营不必点进去判断。现在 `impact()`（`Admin.tsx:52-77`）已经在做这件事，把它扩展到举报与异议即可。
- 必须有一个**「今天还有 N 条超时」的计数**，挂在顶栏。没有这个数字，兼职运营不会主动去看。

### 3.3 通知系统的运营负担

**问题不是「发不发」，而是「发了没人回怎么办」。**

- 当前没有邮件、没有短信通道（`README.md:333`「收不到邮件」）。所以通知只能是站内消息——这意味着**用户不登录就永远看不到**。而实测最近真实投稿是 11-16，之后没有真实内容产生（B4），也就是说**几乎没有活跃用户会登录**。通知系统上线初期会接近零投递、零阅读。
- 反过来，如果为了通知去接邮件，就要处理退信、垃圾邮件、送达率、投诉——这是一个人做不了的运维面，且会把 PII（邮箱）引入当前刻意不要邮箱的模型（`README.md:43`）。
- 「发了没人回」在举报场景下有法律含义：通知了当事人但当事人不回应，平台可以按 1195 的「转送」完成义务并继续处置。所以通知的价值主要是**留痕**，不是沟通。

**建议**：
- 只做站内通知，不做邮件/短信。通知的唯一强制场景是**举报处理结果告知举报人**与**下架告知作者**（这两条有法定义务性质），其余（关注动态、投稿通过）为可选、默认关。
- 每条通知带「送达状态」概念不需要做，但**必须留发送记录**（谁、何时、什么内容），用于事后举证。
- 明确「通知不回复不等于默认同意」，处置不依赖当事人回复。这句话要写进协议。

### 3.4 各功能的运营成本排序（含建议）

| 功能 | 一次性成本 | 持续成本 | 结论 |
|---|---|---|---|
| Token 兑换（装饰类） | 中（兑换表 + 防刷） | 低 | 可做，但价值低 |
| Token 兑换（曝光类） | 高（广告合规 + 标注体系） | 中 | **不做**（见 1.7 与 2.1） |
| 文章编辑 | 高（revision 表 + 重新审核 + 外链审查） | **很高**（每篇编辑都要再审一次） | **降级为「下架 + 重投」** |
| 文章删除 | 低 | 低 | 可做（软删除语义已有） |
| 评论删除 | 低 | 中（要处理回复链与证据留存） | 可做，但必须软删除 + 占位 |
| 头像 | 中（存储 + 转码 + 审核） | 中（每张图都要看） | **砍掉上传，改内置图案库** |
| 举报 | 中 | **高**（这是唯一持续产生人工工作的功能） | **必须做**，但要限流 + 分级 + 回执 |
| 关注 | 中 | 中（通知 fan-out） | 只做对象订阅，不做用户关注 |
| 站点对比 | 低 | 低（但要盯数据诚信） | 可做，带 2.3 的约束 |
| SEO | 中 | 低（但要先清 demo） | **暂缓**，等 B1/B2/B3 解决 |
| 账号注销 | 高（墓碑 + 匿名化 + 封禁联动 + author 降级） | 低 | **必须做**，但排在举报之后 |

**建议砍掉的**：头像上传（改为 8 个内置图案 + 颜色）、文章编辑（改下架重投）、用户间关注（改对象订阅）、Token 曝光兑换。
**建议降级的**：通知（只保留法定义务三类）、对比页（只做同口径、不排除 demo 就不上线）。
**必须做的**：举报（含回执与留痕）、账号注销（含 handle 墓碑）、评论删除（软删除）。

## 4. 安全与滥用

攻击面按「新功能 × 现有实现」列。每个新功能都会继承现有的弱底：进程内/库内限流可被多账号绕过、管理接口只有 Bearer 一道门、明文 HTTP。

### 4.1 文章编辑

| 攻击 | 具体做法 | 后果 | 现有防线 |
|---|---|---|---|
| 绕过审核 | 调编辑接口，走 `moderation.ts:43` 的 `store.put` 路径 | 已审核内容被静默替换 | **无**。`reviewPost` 对已物化文章就是直接写 |
| 审核后改指向 | 通过审核后把外链换成返佣链接/钓鱼站 | 用户点击到平台背书的恶意站 | **无**。`Markdown.tsx:12` 不限制域名 |
| 洗白来源 | 编辑时把 `source` 改成 `user` 以获得 Markdown 渲染 | 来源标签失真（C2 突破） | 需服务端字段白名单 |
| 内容漂移 | 反复小改，规避「一次审核」 | 举报/争议的证据链失效 | 需版本表 |
| 编辑他人文章 | 若 id 可猜（`sub-<投稿id>`、`feishu-<recordId>`）且缺少归属校验 | 越权改他人内容 | 需 `authorHandle === this.user` 校验 |

**缓解**（按优先级）：服务端字段白名单（只允许 title/summary/body）→ 归属校验 → 编辑后强制 pending → 外链变更展示 → `rel="nofollow ugc"`。

### 4.2 举报

| 攻击 | 具体做法 | 后果 | 缓解 |
|---|---|---|---|
| 淹没审核台 | 脚本批量举报正常内容 | 真举报被埋、运营放弃处理 | 每账号每目标一次（唯一约束）+ 每账号每日配额（复用 `AttemptLimiter` 模式，`app.ts:236-251`）+ 同目标 N 人举报才进「待处理」，单条举报进「观察池」 |
| 举报自己刷 | 自己举报自己以获得「已被处理」的假象 | 内容被误标/误恢复 | 禁止举报自己的内容（直接 400） |
| 恶意举报压制差评 | 商家组织多人举报差评 | 商业诋毁的执行端（1.1） | **举报永不自动下架**；差评类只走「事实性异议」通道 |
| 探测隐私 | 通过举报表单看回执是否暴露他人信息 | 泄露被举报人身份 | 回执只说「已收到」，不返回目标详情 |
| 举报即留证 = 二次存储 PII | 举报快照保存被举报内容全文 | 违反最小必要（1.3） | 快照只存 id + hash + 命中片段；保留 90 天 |
| 无凭证举报 | 未登录也能举报 | 刷量无成本 | 举报必须登录（评论已要求登录，`app.ts:857` 走 `route()` 的 401 逻辑） |

### 4.3 关注

| 攻击 | 后果 | 缓解 |
|---|---|---|
| 批量关注（脚本） | 关注表暴涨、通知 fan-out 打爆单进程 | 每账号每分钟上限（与投票共用一只桶即可，`app.ts:848-853`）+ 每账号关注总数上限（如 200） |
| 刷关注数 | 若展示「N 人关注」，可用小号堆数字制造权威感 | **不展示订阅数**，或只展示区间 |
| 隐私画像 | 公开「谁关注了这个站」＝公开用户兴趣 | 永不公开关注者列表 |
| 关注 → 定向推送不实信息 | 见 2.7 | 通知文案中性、带来源标签 |
| 死关注 | 站点下架/文章删除后关注悬空 | 级联隐藏或标注「目标已下架」 |

**实现注意**：follow 表要 `PRIMARY KEY (userHandle, targetType, targetId)`，与 `votes`/`favorites` 同构（`database.ts:38-47`），复用 `targetType ∈ (post, station)` 的既有约束；新增 `model` 类型时要同步改 CHECK——老库改不了 CHECK（`README.md:337`），必须在应用层兜。

### 4.4 头像（当前实现决定了这是最难的一块）

**关键事实**：`avatar` 字段存在但**永远是空串**——注册写 `''`（`app.ts:606`）、种子写 `''`（`seed.ts:34`）；前端根本不用它，头像由昵称哈希出的字与底色生成（`web/src/components/visuals.tsx:54-60`，`Avatar` 只接收 `nickname`）。`UserCard` 用的也是 CSS 空 span（`UserCard.tsx:135`）。

所以「加头像」不是加一个上传框，而是**换掉整套头像机制**，并引入下面全部问题：

| 攻击/风险 | 具体机制 | 后果 | 缓解 |
|---|---|---|---|
| SVG XSS | 上传含 `<script>` 的 SVG，同源 `/avatars/x.svg` 直接访问时执行 | 盗会话（cookie 是 HttpOnly，但可代发请求 + 读页面内容） | **不接受 SVG**。服务端解码重编码为 WebP/PNG，剥离全部元数据；返回时固定 `Content-Type: image/webp` + `Content-Disposition: inline` + `X-Content-Type-Options: nosniff` |
| 伪装扩展名 | 上传 `.png` 实为 HTML/SVG | MIME 嗅探执行 | 用魔数判断而非扩展名；`nosniff` 已有（`static.ts:13`）但只作用于静态目录，上传响应要单独加 |
| 外链追踪像素 | 头像填 `https://evil/x.png` | 每个看页面的人的 IP/UA 泄给第三方 | **只允许站内路径** `/avatars/<id>.webp`，字段存 id 不存 URL。注意：当前 CSP `img-src 'self' data:`（`static.ts:12`）已经挡住了外链图——**一旦为了头像放开 `img-src https:`，同时就放开了所有 Markdown 图片的追踪像素**。这是最容易顺手做错的一步 |
| 内容违规 | 色情/政治/二维码/联系方式 | 合规风险 + 每条都要人看 | 上传进 pending，人工审核通过才展示；默认显示图案头像。或者干脆用内置图案库（见 3.4） |
| 存储爆炸 | 无大小/尺寸限制 | 单进程磁盘写满（容器卷） | 上限 256KB、强制 256×256 重编码、每账号 1 张覆盖式存储 |
| **备份失效** | 备份脚本只对数据库 `VACUUM INTO`（`deploy/zhidedeng-docker-backup.sh:22-31`） | 恢复后所有头像变空，而用户以为永久保存 | 头像必须**存进库里**（BLOB 或 base64，256×256 WebP 约 10–20KB）而不是文件系统；否则备份脚本与恢复演练（`README.md:149-166`）都要同步改，而这两处最容易漏 |
| 注销后残留 | 头像文件不随账号删除 | 违反删除义务 | 与 1.5 联动，注销时一并删 |

**结论**：头像的性价比是全套功能里最低的一项。推荐**内置图案库 + 自选颜色**（无需上传、无需审核、无存储、无 XSS 面），把 `avatar` 字段存成 `preset:07` 这类枚举。

### 4.5 账号注销

| 攻击 | 机制 | 后果 | 缓解 |
|---|---|---|---|
| 同名重注册继承身份 | `handle` 是内容里的作者引用（`service.ts:84`） | 新用户接管旧文章/达人榜/投票影响 | `retired_handles` 墓碑（1.5） |
| 注销逃避封禁 | `setAccountDisabled` 只置 `disabledAt`（`moderation.ts:83`） | 换个号继续 | 封禁记录进墓碑表，禁注册；被封禁账号拒绝自助注销 |
| 注销 → `author()` 崩溃 | `store.get('user', handle)!`（`service.ts:167`） | 首页/详情 500 | 注销功能上线前必须先改这个非空断言 |
| 误注销 / CSRF | 注销是无 body 的 POST，`app.ts:289-300` 对无 body 的写接口**不校验 Content-Type** | 跨站表单可直接触发注销 | 注销必须要求 body（含密码或确认短语）+ 冷静期 |
| 双花/并发 | 同时点两次 | 部分删除、留下孤儿 | 单事务 + 幂等状态机 |

**注意**：`app.ts:289-300` 的 Content-Type 闸门对「无 body 的写接口」是放行的（注释明说 DELETE/restore 允许没有）。`POST /api/checkin` 已经被记录为「唯一不限频+有写入+有奖励」的空档（`README.md:370`）。注销若做成无 body 的 POST，就是第二个这样的空档，而且后果不可逆。

### 4.6 Token 兑换

| 攻击 | 后果 | 缓解 |
|---|---|---|
| 多账号刷签到 | 兑换物通胀 | 签到已是每账号每日一次 + 5 次/小时限流（`app.ts:250`、`service.ts:526-538`）；再加兑换物总量上限 |

| 汇率被营运临时改动 | 历史兑换无法复算 | 流水记下当时汇率与物品版本 |

| 问题 | 机制 | 缓解 |

## 5. 现有部署形态会把哪些风险放大

| # | 现状 | 被哪个新功能放大 | 放大后的具体后果 |
|---|---|---|---|
| D1 | 无 nginx、端口直映射、局域网可达（B1/B2） | 举报、关注、注销、管理台重构 | 所有新增写接口都在明文 HTTP 上。举报内容含「某站跑路」这类指控，明文传输＋无访问日志＝被窃听后平台无法自证「未泄露」。注销/编辑是**不可逆写**，被重放或被冒名执行的代价远高于发一条评论 |
| D2 | `TLS_ENABLED=0` → cookie 无 `Secure`（`app.ts:225-235`） | 全部登录态功能 | 同局域网嗅探即可接管会话；接管后可发起批量关注、恶意举报、替他人注销。**注销功能使「会话被盗」从骚扰升级为毁号** |
| D3 | 管理接口唯一门是 32 位 Bearer，且对整网段可达（`README.md:200`） | 举报台、审核台重构、编辑审计 | 审核台会从「偶尔用 curl」变成「日常操作的界面」，密钥暴露面与使用频率成正比；`sessionStorage` 只防关页残留（`web/src/admin.ts:7-18`），不防同机 XSS 与嗅探。且现在**没有管理员操作审计**（只有三条 `console.info`：`app.ts:414`、`agent-tokens.ts:61`、`agent-tokens.ts:84`）——举报处理、内容下架、账号注销全都无法追溯「谁在何时以什么理由做的」 |
| D4 | `SITE_MODE=demo` + 生产库含演示数据（B3） | SEO、对比、举报、关注 | 见 2.2 与 2.3：虚构站被索引后不可撤回；对比页里虚构站看起来数据最全；对虚构站举报会产出「对不存在主体的投诉」记录，污染留痕 |
| D5 | 备份只覆盖 DB、每天一次、留 14 份（`README.md:127-137`） | 编辑、删除、注销、头像 | 编辑覆盖正文后，旧版本只有在「昨天之前的备份」里，RPO 24h；注销是真正的删除，备份里仍有，形成「已删除但仍在备份」的矛盾；头像若落盘则完全不在备份内 |
| D6 | 单进程 + 同步 SQLite；批量审核 500 条约 8 秒阻塞（`README.md:369`） | 通知 fan-out、举报队列、关注动态 | 关注/通知会在一次写操作里触碰大量行，阻塞期间 `/api/health` 也要排队；一个恶意账号的批量关注就能让健康检查超时，触发错误告警 |
| D7 | 限流多为进程内或单库（`README.md:334`、`app.ts:236-251`） | 举报、关注、兑换 | 多账号即可绕过按账号上限；举报与关注是「可被小号放大」的典型，需要按目标去重而非只按来源限流 |
| D8 | 飞书同步未部署、内容只减不增（B4） | 通知、关注、SEO | 通知系统上线即空转；关注没有更新可推；RSS 没有更新，订阅者会认为站已死。三者都会让产品显得「坏了」，而实际是供给问题 |

## 6. 建议

### 6.1 分级结论

**A. 必须做（缺了就不能继续公开运营）**
1. **举报入口 + 回执 + 处理留痕**（含分类、SLA、反通知路径）。这是法定义务，且是避风港的前提。
2. **账号注销**（含 `retired_handles` 墓碑、`author()` 降级、封禁联动、冷静期）。
3. **评论删除**（软删除 + 前台占位 + 父删子隐）。
4. **主体与规则公示**：运营主体、备案号、隐私政策、用户协议、社区规范、举报渠道。`/business` 的「联系方式待配置」必须落地。
5. **管理员操作审计**（who / when / why / what），覆盖审核、下架、恢复、举报处置、注销。

**B. 必须配套运营流程才能做**
6. **站点对比**：只在「同口径 + 排除 demo + 不显示全空列」三条同时满足时上线。
7. **对象订阅 + 站内通知**：只做三类法定义务/关系型通知，不做营销型推送。
8. **Token 兑换**：只做非曝光类兑换物。
9. **SEO**：必须排在 `purge:demo`、域名、HTTPS 之后；OG 描述与 `SITE_NOTICE` 收敛为同一常量。

**C. 建议砍掉或降级**
10. **头像上传** → 降级为内置图案库（理由：备份不含文件、SVG XSS、CSP 一旦放开就连带放开所有图片追踪、每张都要人审）。
11. **文章编辑** → 降级为「下架 + 重新投稿」（理由：无 revision 表就必须直写 `entities`，等于绕过审核；有 revision 表则是本次评审里最贵的一项）。
12. **用户间关注** → 降级为对象订阅（理由：社交图谱 + 粉丝数刷量 + 算法推荐合规 + 骚扰，四项成本同时出现）。
13. **Token 曝光兑换** → 不做（理由：与 `Business.tsx` 的公开承诺冲突，且把 UGC 变成平台广告）。

### 6.2 上这些功能之前必须先解决的前置条件清单

**P0（阻断级，任一未完成则不得上线任何面向公众的写功能）**

| # | 前置条件 | 验收标准 | 对应风险 |
|---|---|---|---|
| P0-1 | 域名 + HTTPS 反代（或至少内网 TLS），`TLS_ENABLED=1` | `curl -I https://<域名>/api/health` 返回 200；cookie 带 `Secure`；`/api/admin/` 非白名单 403 | D1、D2、4.5 |

| P0-3 | 清理演示数据 | `pnpm purge:demo --db=... --apply` 后 `SELECT count(*) FROM entities WHERE json_extract(data,'$.source')='demo'` 为 0；`/api/health` 的 `mode` 为 `production` | B3、2.2、2.3 |
| P0-4 | 隐私政策 + 用户协议 + 社区规范 + 举报渠道页 | 四页可访问、内容含数据保留期与删除方式、举报渠道真实可用 | 1.6、1.4 |

### 6.3 建议的上线顺序

```
第一批（合规托底，不产生新内容入口）
  举报（含回执/留痕/反通知） → 评论删除 → 账号注销 → 管理台合并重构 + 审计
  同时完成 P0-1…P0-8

第二批（数据诚信相关的只读功能）
  站点对比（带 2.3 三条硬规则）→ Token 装饰类兑换

第三批（等供给恢复后再做）
  purge:demo → 域名/HTTPS → SEO（sitemap/RSS/OG）→ 对象订阅 + 站内通知

第四批（重新评估，当前不建议）
  头像上传、文章编辑、用户关注、Token 曝光兑换
```

理由：第一批全是「不解决就有法律责任」且**不增加内容供给压力**的功能；第二批是只读、可回滚；第三批依赖 B1/B2/B3 全部解决且飞书同步恢复（否则上线即空转）；第四批每一项的持续运营成本都超过一个兼职运营的预算。
