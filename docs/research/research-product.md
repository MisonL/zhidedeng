> 调研方式：通读 `README.md`、`docs/spec.md`、`docs/plan-agent-submission-v2.md`，逐页读 `web/src/pages/` 与 `web/src/components/`，再回到 `server/src/` 核对每条结论的数据来源。

## 0. 一句话诊断

**产品把「工具」做完了，把「社区」的入口位置留空了。**

站点库、模型库、比价表、值/不值、评论、投稿、审核台、Agent 接口——一条完整的社区骨架都在，1285 个测试也都在跑。但生产上**真实内容产出为 0**：唯一一篇真实投稿被拒，Agent 通道产出的 3 个站是测试站且已下架，飞书同步在生产未部署（README「定时同步」一节）。

所以问题不是「功能不够」，而是：

1. 站点页有 9 个指标位，5 个永远显示「暂无」（`web/src/pages/Stations.tsx:106-116`），而唯一能填满它们的东西（真实用户的碎片化经验）**没有任何入口**；
2. 唯一愿意投稿的人被拒了，且产品结构上**无法告诉他为什么**（见 §4.2，这是本文最尖锐的发现）；
3. 签到发出去的 Token 永远花不掉（`server/src/service.ts:535` 是唯一写入点，只加不减），贡献者在站内的身份沉淀为零（`avatar` 恒空、无个人主页、达人榜不可点）。

## 1. 目标用户画像

四类角色，按「他打开这个站的第一个动作」区分。**判断标准：他在 30 秒内能不能拿到他要的东西；拿不到，他会不会成为下一个贡献者。**

### A. 「刚上车的新手」——小吴，24 岁，独立开发者，第一次用 API

| 维度 | 内容 |
|---|---|
| 要解决的问题 | 官方 API 太贵/开不了卡，听说「中转站」便宜，但完全不懂「倍率 / 分组 / 官转 / 逆向 / 号池」这些黑话，怕被骗。 |
| 打开场景 | 在群里/小红书看到某站名，或者搜「XX 中转 靠谱吗」落到本站；也可能是 ChatGPT 让他「去查一下这个站」。 |
| 现有功能哪里挡住他 | ① 站点页九宫格里「可用率 / 首 token 延迟 / 成立时间 / 运行状态 / 综合得分」全是「暂无」（`Stations.tsx:106-116`），他不知道这是**没有数据**还是**数据不好**；② 页面没有一句「这个站最近有没有人用过」；③ 没有举报/避坑记录；④ 评论区的 95 条全是种子（生产事实），他看到的「热闹」是假的。 |
| 会不会贡献内容 | **会，而且是最可能贡献的一类**——但他能贡献的是「充了 10 块，能用/不能用」这种 20 个字的信息，而站内唯一的表达入口是 2000 字评论（`web/src/components/Comments.tsx:12`）或三段式长文投稿（`web/src/pages/Submit.tsx:240-262`）。门槛高了两个数量级，他直接关页面。 |

**给他的设计含义**：需要一个「一句话反馈」入口，和「这个站最近有人确认过」的时间信号。

---

### B. 「算成本的团队采购 / 接私活的开发者」——老陈，34 岁，给客户做 AI 应用

| 维度 | 内容 |
|---|---|
| 要解决的问题 | 同一批流量（输入为主还是输出为主）放在哪个站最省；起充门槛多少、能不能开票、退款条款；要能拿一份**能贴到周报/给老板看**的对比。 |
| 打开场景 | 每月续费前、客户问「能不能压成本」时、现有站涨价/限流时。**低频但高价值**，一次决策可能带来 3~5 个新用户（他会把链接发给同事）。 |
| 现有功能哪里挡住他 | ① 模型页比价表有 8 列（`web/src/pages/Models.tsx:117`），但没有「起充额 / 充值费率」——这两个字段在 `Station` 上有（`rechargeThreshold`、`paymentMethods`），却没出现在最需要它的比价表里；② 没有并排对比 2~3 个站的功能（缺口 7），只能用浏览器开三个 tab 人肉对；③ 同一个模型一个站只能有一条报价（README「已知未修」：主键是 `(stationSlug, modelSlug)`），「输入 0.3 / 输出 0.9」这种双价登记不进去，而这恰好是采购最想看的；④ 不能导出。 |
| 会不会贡献内容 | **不会主动写长文**，但他会做一件事：把「我在 3 个站各充了 20 块跑了一周」的结论发在群里。产品要做的不是求他写文章，而是给他一个**填表格 30 秒就能留下的结构化记录**，并允许他导出。 |

**给他的设计含义**：对比页 + 可导出；把「起充/支付方式」搬进比价表。

### C. 「爱写评测的活跃群友」——阿哲，27 岁，L 站/微信群常驻，写过 20 篇中转站测评

| 维度 | 内容 |
|---|---|
| 要解决的问题 | 想被看见、想有话语权、想「我的判断被验证是对的」；顺带希望有人通过他的链接/邀请码进来（但他知道本站不允许硬广）。 |
| 打开场景 | 新模型发布、某站出事、自己刚踩坑/刚发现宝藏站——**情绪峰值时刻**，通常是在手机上、在群里聊到一半。 |
| 现有功能哪里挡住他 | ① **发完不能改**（只有 `createPost`，`shared/src/routes.ts:30`；全文无 update/delete 文章路由），打错一个字只能求管理员；② 不能删自己的评论（`Comments.tsx:97` 只有「回复」按钮，只有管理员能 hide）；③ 没有头像（`avatar` 恒空：`server/src/app.ts:606`、`server/src/service.ts:266`），全站头像都是昵称首字（`web/src/components/visuals.tsx:54-58`）——**在评测社区里这是致命的身份缺失**；④ 没有个人主页（`web/src/App.tsx:22-43` 无 `/u/:handle`），达人榜的卡片**连点都点不进去**（`web/src/components/RankingBoard.tsx:53-58` 的 `RankCard` 没传 `to`；`RankCard` 定义在 :17，:30 处 `to` 为空即渲染成不可点的 `<div>`）；⑤ 正文里的图放不出来：`Markdown` 不处理图片（`web/src/components/Markdown.tsx:1-19`），CSP 是 `img-src 'self' data:`（`server/src/static.ts:12`），外链图会被拦；⑥ 投稿后不知道审到哪了，只能自己回「我的」刷（无通知系统）。 |
| 会不会贡献内容 | **本来是最应该贡献的一类，现在被 6 个体验缺口劝退。** 而且他贡献的动机是「身份 + 影响力」，本站目前**一点都给不了**：没有主页、没有头像、不能编辑、不能被关注。 |

**给他的设计含义**：编辑/删除、作者主页、头像、通知、图片——这 5 件事不是「锦上添花」，是这类用户的**准入门槛**。

### D. 「跑 Agent 自动采集的自动化用户」——小林，30 岁，自己维护一个 NewAPI 站的监控脚本

| 维度 | 内容 |
|---|---|
| 要解决的问题 | 他有 20 个站的报价快照，想同步到一个公共库，让别人也受益（同时给自己站引流，只要不硬广）。他不想手动填表。 |
| 打开场景 | 定时任务跑 `zdd submit`（`scripts/zdd.ts`）；或者第一次读到 `/docs` 页（`web/src/pages/Docs.tsx`）决定接不接。 |
| 现有功能哪里 hurt 他 | ① 凭据门槛：注册满 7 天或有 1 篇 approved 站内投稿（README「Agent 提交接口」），**新账号直接被挡**；② 提交后**没有回执闭环**——只有 `/api/agent/status` 轮询，没有 webhook，也没有「你的第 N 条被拒，理由是 X」的推送；③ 报价整包替换语义（README「已知未修」）意味着他每次必须提交全量，否则会删掉别人的报价；④ 提交进来的内容全部 pending，而审核台是要人守的（`web/src/pages/Admin.tsx`），他的贡献会堆在队列里半个月。 |
| 会不会贡献内容 | **已经在试了**：6 个 Agent 凭证、5 条 approved 的 agent 投稿、3 个测试站——这是全站唯一「有人真的动手」的证据。但产出被下架了，说明**通道通了、价值没通**。 |

**给他的设计含义**：这条通道是**最便宜的冷启动燃料**（机器不需要激励，只需要闭环和信任），但它喂进来的内容必须能被快速消化，否则只是把审核台压垮。

### 画像小结

| 角色 | 核心诉求 | 贡献意愿 | 当前最大阻塞 | 贡献形态应该是 |
|---|---|---|---|---|
| A 新手 | 「这站能不能用」 | 中（会写一句） | 无轻表达入口 | 一句话反馈 / 打不开报告 |
| B 采购 | 「哪个最省 + 能交差」 | 低（会填表） | 无比对、无导出、缺字段 | 结构化对比记录 |
| C 写手 | 「被看见」 | 高（被劝退） | 不能编辑/无主页/无头像/无通知 | 长文 + 修订 + 主页 |
| D 自动化 | 「同步得进去、有人审」 | 高（已在做） | 门槛 + 无回执 | 批量 upsert + 状态推送 |

**关键判断：A 和 D 是冷启动阶段唯一现实的供给侧；C 是中期护城河；B 是付费/传播侧但目前没有可付费的东西。**

## 2. 核心使用场景走查

每个场景写清「他点哪里 → 看到什么 → 缺什么 → 结论」。

### S1｜「这个站还能不能充钱」——最高频、当前完全无解

1. 首页搜索框输入站名（`web/src/components/Layout.tsx:44-52`）→ `/search?q=`（`web/src/pages/Search.tsx`）。
2. 点站点卡 → `/stations/:slug`。
3. 看到九宫格（`Stations.tsx:106-116`）：
   - 最低倍率：有（如果有 blended 报价）
   - 可用率：**暂无**
   - 首 token 延迟：**暂无**
   - 成立时间：**暂无**
   - 运行状态：**暂无**（生产里 `status` 永远为 null——Agent 入口禁写，飞书不采，只有种子里有）
   - 综合得分：**暂无**（`server/src/service.ts:243`：`uptime === null` 时 score 为 null）
4. 往下：模型倍率表（`Stations.tsx:117-133`）——3 行数字，但用户此刻要的不是价格，是「这站是不是明天就跑」。
5. 相关文章（`Stations.tsx:139-148`）：**空**。
6. 评论（`Stations.tsx:138`）：空 / 或演示数据里的假评论。

**缺什么（按重要性）**：
- **「社区最后确认时间」**：这个信息完全可以从已有数据算出来——该站最近一条 approved 投稿/评论的时间。为 null 就显示「暂无社区反馈」。**不需要任何实测能力，不违反数据诚信**，却直接回答了「最近有没有活人在用」。这是本文认为性价比最高的一个新增字段。
- **「报告打不开 / 报告跑路」入口**：用户主观断言，不是平台实测。聚合成「最近 7 天有 N 人报告打不开」，比任何编造的可用率都诚实且有用。
- **风险历史**：apiranking 用「换域名公告」解决（<https://apiranking.com> 顶部横幅），本站完全没有位置记录这件事。

**结论**：这个场景今天必然失败，且失败原因是「无数据可给」，不是「UI 不好」。修法必须是**引入用户断言**，而不是引入探测或估算。

---

### S2｜「同一个模型，哪个站最便宜」

1. `/models` → 点模型 → `/models/:slug`（`web/src/pages/Models.tsx:80-157`）。
2. 比价表 8 列：站 / 倍率 / 计价口径 / 报价时间 / 可用率 / 首 token / 状态 / 操作（`Models.tsx:117`）。
3. 页面顶部已经有一句正确的口径说明（`Models.tsx:104-111`），最低价只在同口径内高亮（`Models.tsx:122`）——**这块做得是对的，是全站最成熟的一段**。
4. 但采购真正要算的是「我这个月的账单」，需要：
   - 起充额（`rechargeThreshold` 在 Station 上有，**不在此表**）
   - 输入/输出分别的倍率（主键限制，做不到，README 已知）
   - 并排对比（缺口 7，做不到）
   - 导出（做不到）

**缺什么**：把 Station 上的 `rechargeThreshold` / `paymentMethods` 并进比价表（**这是纯前端 + 一个 DTO 字段，成本极低**）；新增 `/compare?stations=a,b,c`（见 §6 批次 2）。

**结论**：工具侧已经 70 分，差的 30 分全在「能不能拿去算账」。

---

### S3｜「我在用这个站，想留一句话提醒别人」——**流失最严重的一步**

1. 站点页底部评论框（`Comments.tsx:77-79`）：`placeholder="说说你的真实体验…"`，`maxLength=2000`（`Comments.tsx:12`、`:40`）。
2. 他想说的是：「充了 10 块，第二天开始 502，客服不回」——20 个字。
3. 他面对的是一个 3 行 textarea 和一个空评论区，**没有任何结构提示**（用多久了？什么用途？退款了没？）。
4. 写完发布即公开（无审核），**不能编辑、不能删除**（`Comments.tsx:97` 只有「回复」；只有管理员能 hide）。
5. 更糟的是：评论**不进搜索**（`Search.tsx:14-16` 只搜 models/stations/posts），写完等于扔进黑洞。

**缺什么**：
- 结构化轻反馈（≤120 字 + 3 个可选项：使用时长 / 主要用途 / 是否遇到退款或跑路）；
- 评论进入搜索索引；
- 自删（5 分钟内可删，或任何时候软删）。**写手最怕的不是没人看，是写错了撤不回。**

**结论**：这一步是「A 角色」变成贡献者的唯一入口，今天它的转化率是 0。

---

### S4｜「验证一个站是不是掺水/降智」

1. 用户想查「这站的 Claude 是不是满血」。
2. 本站**结构上不可能回答**：Agent 入口禁止 `uptime/status/score` 等字段（`server/src/agent-api.ts` 的 `rejectForbiddenFields`），平台没有探测机制，飞书也不采。
3. apiranking 的做法是真金白银付费调用 + 鹈鹕测试 + 扣费对账（<https://apiranking.com>），这是**重资产业务**，不是一个 SQLite 单人项目该做的。
4. 但 apiranking 页面上真正被用户读的，其实是**人写的那句话**：「💬站长纯技术出身，给我感觉人挺实在」。

**缺什么**：本站该抢的正是这句人话。做法是把「掺水/降智」的讨论**变成结构化标签 + 主观断言 + 明示「用户自述，未经平台核实」**，而不是去测。

**结论**：明确**不做实测**（与硬约束冲突且成本极高），改做「主观经验的聚合与检索」。这条取舍必须写进产品原则，否则未来一定有人提「加个可用率探测」的需求。

---

### S5｜「我投稿了，然后呢」

1. `/submit` 提交成功 → toast「已提交，审核通过后公开」→ 跳 `/me?tab=posts`（`Submit.tsx:141`）。
2. 但站内文章走的是 `entities` 直接写 pending（`server/src/service.ts:749-760`），模型/站点推荐走 `submissions`（`Submit.tsx:73-135`），两套数据。
3. 「我的」页分成 4 个 tab：我的收藏 / 我的分享 / 我的投稿 / 账户设置（`web/src/pages/Me.tsx:16-22`）。**文章在「我的分享」，站点和模型在「我的投稿」**——用户被 toast 送到 `tab=posts`，去错了地方就找不到自己刚提交的站点推荐。
4. 更致命：**文章被拒时没有任何理由**。
   - 审核台的文章页签（`Admin.tsx:484-512`）**没有理由输入框**，只有一个「拒绝」按钮；
   - 服务端 `reviewPost` 只写 status（`server/src/moderation.ts:43`）；
   - `Post` 的 `reviewReason` 字段只对队列投稿派生（`server/src/service.ts:481`），`entities` 里的文章记录**没有这个字段的落地位置**；
   - 只有 Agent 通道被强制要求理由（`server/src/submissions.ts:930`），站内用户反而没有。
5. 生产上唯一一篇真实投稿，就是走的这条路径，且是 rejected。

**缺什么**：文章通道的驳回理由必须**落到数据模型**（`post.reviewReason` 或 `submissions` 统一），审核台文章页签必须**强制填写**，模板直接复用已有的 `REJECT_PRESETS`（`Admin.tsx:23`：报价与页面不一致 / 站点无法访问 / 与已有投稿重复 / 内容含广告或推荐语 / 字段填写有误）。

**结论**：这是全站唯一一个「已经有人做了，却被产品弄丢了」的用户。**它的修复成本是一天，收益是「下一个投稿的人不会再无声消失」。**

---

### S6｜「Agent 自动同步」

1. 读 `/docs`（`Docs.tsx`）→ 看到 `/api/agent/stations` 的说明。
2. 生成 token：`POST /api/account/agent-tokens`，需要 7 天账号龄或 1 篇 approved 投稿（README）。
3. 提交 → `pending`，`autoApproved: false` 强制人工（`server/src/agent-api.ts`）。
4. 轮询 `/api/agent/status` → 看到 pendingCount / quotas / submissions。
5. 等。等到管理员打开审核台。

**缺什么**：审核 SLA 的**对外承诺**。哪怕只是「通常 48 小时内处理」，也能把一个愿意贡献的自动化用户从「提一次就跑了」变成「每周同步一次」。

## 3. 竞品与参照物分析

### 3.1 什么值得买（smzdm）—— 最该学的与最不能学的

| 机制 | 值得借吗 | 说明 |
|---|---|---|
| 「值 / 不值」二元投票 | 已有 | 本站已实现（`VoteButtons.tsx`），且比 smzdm 更克制（只显示比例，不显示绝对热度） |
| 爆料众测、按内容表现动态结算 | **不借** | smzdm 的奖励与「引导成交」挂钩，而本站一旦把奖励与「引导去某站充值」挂钩，就是变相返佣，直接与 `Business.tsx:17`「榜单和评价不接受付费改动」矛盾 |
| 优质内容给「金币」，金币能换实物 | **借形式，不借标的** | 详见 §5：奖励存在，但兑换物只能是站内能力与身份，不能是现金/返利 |
| 作者主页 + 等级 + 勋章 | **强烈建议借** | 本站一个都没有，这是 C 角色流失的主因 |
| 「好价」结构化字段（价格/渠道/时间） | **强烈建议借，但换标的** | smzdm 记价格，本站记**倍率 + 口径 + 报价时间**（已有 `basis`/`quotedAt`），方向是对的；缺的是把「起充/退款」这类**决策字段**也结构化 |
| 站内通知（评论被回复、爆料被采纳） | 借 | 本站完全没有，导致「审核结果」只能靠用户自己回来查 |
| 爆料前的「重复检测/相似度提示」 | 借 | 本站有 payloadHash 幂等，但对用户侧无提示（提交重复只会得到一个 409 或静默合并） |

**smzdm 的核心洞察**：它卖的不是「价格」，是「**替你省掉了决策成本**」。本站今天把「倍率」摆得很清楚，但没替用户省掉「这站靠不靠谱」这个更大的决策成本。

### 3.2 apiranking.com —— 生态里最接近的形态，但走的是重资产路线

- 首页即「实测排行榜」，列：倍率、真假检测、掺水检测、**应扣 vs 实扣对账**、缓存命中率、平均等待、起充额、退款手续费、开票门槛（<https://apiranking.com>）。
- 变现靠**首充返利码 / 本站用户专属优惠码**（页面上到处是 `【本站用户专属】首充赠 10%兑换码`）。
- **可借**：「扣费对不上标价」「缓存命中」这类**用户真会痛**的维度；「起充 / 退款手续费 / 开票」三件套（本站只有 `rechargeThreshold`，没有后两个）。
- **不可借**：① 所有实测指标（本站无探测能力，硬约束禁止）；② 返利码变现（会立刻污染社区判断的可信度，也让「不写绝对价格」的约束失效）；③ 真假检测的结论性表述（"模型为真"是平台断言，本站只能承载"用户自述"）。
- **值得警惕**：它用「最近更新 2026-11-24 16:04」这种**新鲜度**信号建立信任。本站最缺的正是这个。

### 3.3 grandet.ai —— 机器可读的比价基础设施

- 收录 3064 个站点，把「倍率 + 分组」换算成每百万 token 单价，明写「观察日期」，并提供 MCP / Skill / 查价 API（<https://grandet.ai/zh-CN>）。
- **可借**：① **口径归一化的表述方式**（它把 NewAPI 的黑话做成了术语表，本站已有 `RateBasis`，但没有术语表，A 角色看不懂「0.6x 综合」是什么意思）；② **给 Agent 用的稳定接口**（本站已经有了，甚至更规范——`/api/agent/*` 比 MCP 更简单）；③ 显式的「观察日期」——本站有 `quotedAt`，但大量为 null 时显示"时间未知"（`web/src/format.ts:67-73`），这个处理很诚实，应保留。
- **不可借**：直接展示换算后的绝对单价（本站硬约束：只写相对倍率，不写绝对价格）。

### 3.4 GitHub 导航站（awesome-api-proxy / awesome-ai-api-hub）与 L 站评分站（rate.linux.do）

- 596 个站点的 Markdown 列表，靠 PR 维护，字段是「站名/域名/描述/在线率/倍率」——**信息密度极低，但收录量极大**。
- **可借**：收录的**低门槛**（只要名称 + 域名就能进）。本站 `POST /api/stations/suggest` 已经做到了这一点（只需 name + url，报价可空，`Submit.tsx:204-235`），这是对的。
- **不可借**：它们表格里的「在线率 99.7%」这类**无来源数字**——这正是本站硬约束要防的东西。
- L 站的经验：用户真正会去看的是「**有没有人骂过这个站**」。所以「举报/避坑」不是锦上添花，是核心内容类型。

### 3.5 One Tracker / RelayWatch 类项目

- 自动爬 NewAPI/Sub2API 站点的 `/api/pricing`，做价格聚合（<https://github.com/NekroAI/one-tracker>、<https://github.com/bnlbnf/relaywatch>）。
- **这是本站 Agent 通道的天然上游**：与其等用户手动提交，不如明确「支持 NewAPI 格式的自动上报」——但这属于新能力，不在本次 10 个缺口内，只作为 D 角色的中期方向记录。

### 3.6 三条不能碰的红线（把「不照搬」写成可检查的规则）

1. **不产生任何平台侧实测数字**：没有探测就不写 uptime / latency / score。所有此类字段必须为 null 并显示「暂无」（现有实现正确，见 `server/src/service.ts:243`、`web/src/format.ts:38-41`）。
2. **不出现绝对价格**：只写相对官方价的倍率（`shared/src/domain.ts` 的 `MIN_RATE/MAX_RATE`、`Submit.tsx:157` 的表单提示）。
3. **任何激励都不得影响排序、评分、审核结论**。可兑换的只能是「能力、身份、导出、时效」，不能是「位置」。

## 4. 内容供给的冷启动问题（本文最重要的一节）

### 4.1 现状：三条通道，全部试过，真实产出为 0

| 通道 | 生产实测 | 真实产出 |
|---|---|---|
| web（站内用户） | 1 通过 / 1 拒 | 0 篇公开（唯一那篇 rejected） |
| agent | 5 通过 / 10 拒 | 0（3 个测试站已下架） |
| feishu | 6 通过 / 1 拒 | 停滞在 2026-11-14，**定时同步生产未部署**（README） |

配合 22 个账号、20 个会话、6 个 Agent 凭证、95 条评论 / 237 票 / 30 收藏（全部为种子）——**这不是「内容少」，是「内容生产的回路一次都没闭上」**。

漏斗：22 注册 → 2 次 web 投稿（9%）→ 1 通过率 0% → 公开真实文章 0。

### 4.2 七个具体原因（每条都能指到代码或数据）

**① 生产库里还留着 12 个虚构演示站——它在杀死「这是真实社区」的第一印象。**
生产 15 个站里 12 个是「虚构·XX」。README 明确写过：切模式不清理已有数据，要清就 `pnpm purge:demo --apply`。而全站页脚又常驻一句「带『虚构』字样的站点与内容是演示数据……不构成消费建议」（`web/src/format.ts` 的 `SITE_NOTICE`）。
所以一个真实用户点进来，看到的是：大量带「虚构」标签的站 + 一句「以上均不构成消费建议」。**他凭什么往这里投稿？** 这是冷启动的隐形第一因，且修复成本是一条命令。

**② 唯一的生产者被拒，且产品结构上无法告诉他原因。**
- 审核台文章页签没有理由输入框：`web/src/pages/Admin.tsx:484-512`；
- 服务端只写 status：`server/src/moderation.ts:43`；
- `Post.reviewReason` 只对队列投稿派生：`server/src/service.ts:481`；
- 强制理由只对 agent 通道：`server/src/submissions.ts:930`。

结果：他看到的只有「未通过」两个字（`PostCard.tsx:31`）。**一个愿意写第一篇真实内容的人，得到的唯一反馈是沉默的拒绝。**

**③ 表达形态错配：只有「长文」，没有「一句话」。**
投稿要 kind + 标题 + 摘要 + 正文三段（`Submit.tsx:240-262`，正文 12 行 textarea，服务端上限 10 万字 `server/src/app.ts:771`）。而真实用户手里握着的信息 90% 是碎片：「充了 10 块能用」「今天开始 502」「换域名了」。
这些信息最适合的位置是**站点页的一句话反馈**，而那里今天只有一个 2000 字评论框（`Comments.tsx:12`）。

**④ 贡献没有任何可见回报，连身份都没有。**
- 头像恒空（`shared/src/domain.ts:37`、`server/src/app.ts:606`、`server/src/service.ts:266`），全站用昵称首字兜底（`visuals.tsx:54-58`）；
- 没有作者主页（`App.tsx:22-43`），达人榜卡片不可点（`RankingBoard.tsx:53-58`）；
- 积分只增不减（`service.ts:535` 是唯一写入点；全仓无任何扣减）；
- 没有关注、没有通知（缺口 6）。

**⑤ 审核没有 SLA、没有通知，投稿体验是「扔进黑洞」。**
提交后只能靠 `/me` 自查，而 `/me` 还分 4 个 tab，文章和站点推荐在**不同 tab**（`Me.tsx:16-22`）。

**⑥ 站内没有可消费的内容，所以也没人「因为读到好东西而想写」。**
home 页排行榜（`RankingBoard.tsx`）在真实库里会显示「暂无报价」的模型榜、空的社区榜、「分享 0 · 获值 0」的达人榜。**空榜单是负向激励**：新用户看到"这里没人"，就不会成为第一个。

**⑦ 编辑器太弱，写手写不出「像样的评测」。**
`Markdown` 不处理 `img`（`Markdown.tsx:1-19`），CSP `img-src 'self' data:`（`static.ts:12`）——外链图会被浏览器拦。而中转站评测的**核心证据就是截图**（后台扣费记录、报错页面）。今天写手只能贴文字，这让「有图有真相」的评测文化无法形成。

### 4.3 五个机制设计（按性价比排序，每条给预期效果与代价）

#### M1｜把「已有行为」转成内容：站点页的一句话反馈（**最高优先**）

**做什么**：在站点详情（`Stations.tsx:138` 评论模块之上）新增「使用反馈」：≤120 字文本 + 3 个可选项（用了多久：<1 天 / 1~30 天 / >30 天；主要用途：聊天 / 代码 / 批量；状态：正常 / 不稳定 / 已退款或跑路）。发布即公开，带「用户自述，未经平台核实」标签；每账号每站每天 1 条；可删除自己 24 小时内的反馈。

**为什么有效**：把贡献门槛从「写一篇文章」降到「点 3 下 + 一句话」，直接对准 A 角色的真实信息形态；同时为 S1 场景提供「社区最后确认时间」的数据源（最近一条反馈的时间）。

**预期效果**：把 22 个账号里「用过某站」的人从 0 转化到 5~10 条真实反馈——这已经足够让 15 个站的一半不再是空页面。

**代价**：需要新表 + 新路由 + 出现在审核策略里。**建议不做事前审核**（评论已有「发布即公开 + 频率限制」的先例），但必须提供举报与管理员隐藏。风险是垃圾内容，用「每站每天 1 条 + 需登录 + 最短使用时长声明」压住。

**与硬约束的兼容性**：完全兼容。它存的是用户断言，不是平台实测；页面上明示来源。

---

#### M2｜驳回必填理由 + 审核时效承诺（**成本最低，必须做**）

**做什么**：① 审核台文章页签加理由输入框，复用 `REJECT_PRESETS`（`Admin.tsx:23`）；② 服务端把理由落到文章记录上（新增 `reviewReason` 或统一走 submissions），让 `PostCard`/`PostDetail` 能显示；③ 在 `/submit` 页写死一句「通常 48 小时内审核」（`Submit.tsx:157` 的位置）。

**为什么有效**：它修复的是「唯一的贡献者被沉默拒绝」这个已经发生的事故，并让下一个投稿人知道「被拒是可以改的」。

**预期效果**：投稿→二次投稿的转化从 0 变成可观测（当前连观测都没有）。

**代价**：一天的工作量；需要一次性的数据模型决定（建议直接在 `entities` 的 post 记录上加 `reviewReason`，与 `removedAt` 同类）。

---

#### M3｜「缺稿清单」：把「写什么」从创作者转移到平台

**做什么**：新增 `/wanted` 页（或嵌在首页侧栏 `FeedSidebar` 里）：列出「有报价但没有一篇关联文章」的站点、「被收藏最多但 0 评论」的站点、「搜索了但站内没有结果」的词（需要先做 M5 的搜索日志）。每个条目后面挂一个「我来写这篇 →」按钮，直接跳到 `/submit?kind=review&station=<slug>` 且**预填站点**。

**为什么有效**：写手最大的成本不是打字，是「不知道写什么、写了有没有人看」。平台告诉他「这 12 个站一篇评测都没有，你写第一个」，同时保证「写了就有人看到」（因为页面本来就缺这块内容）。

**预期效果**：把选题决策成本降到 0，直接把 C 角色从「想写」推到「动手」。

**代价**：一个页面 + 一个聚合查询（`offers` 与 `posts` 的差集，已有索引基础）；需要 `Submit.tsx` 支持 `station` 预填参数（现在只支持 `kind`，见 `Submit.tsx:33`）。

---

#### M4｜身份沉淀：作者主页 + 头像 + 可点的达人榜

**做什么**：① `/u/:handle` 主页（文章列表 + 值数 + 加入时间 + 简介，数据全都有：`Post.author.handle`、`service.ts:168`）；② 达人榜卡片加 `to`（`RankingBoard.tsx:53-58`）；③ 头像：**不做上传**，改为「从已认证的第三方地址填一个 URL」或「上传 64×64 到本地」——考虑 CSP `img-src 'self' data:`（`static.ts:12`），**最省的方案是把头像存成 data URI 或本地静态文件**，否则要改 CSP；④ 简介已可改（`Me.tsx:109-147`），但没有任何地方展示——主页一上线它才有意义。

**为什么有效**：C 角色的全部动机是「被看见」。主页是可分享的 URL，是他会把链接发到群里的东西——**这本身就是分发**。

**代价**：主页 = 一个路由 + 一个 DTO；头像如果走文件上传，要考虑存储与审核（建议先只做 data URI / 首字彩色头像的"选择色板"版本，成本几乎为 0）。

---

#### M5｜把「消费行为」变成内容与需求信号

**做什么**：
- **搜索日志**：`getHotSearches` 现在是硬编码的 8 个词（`server/src/service.ts:901-903`），这是全站最明显的一个"假装有数据"。改成记录搜索词（脱敏、只存词与时间），首页热门搜索就用真实数据驱动，同时得到「**零结果搜索词**」——这是最强的选题与补录信号（用户搜了但站内没有 → 要么缺站，要么缺文章）。
- **收藏清单公开化**：「我的收藏」可以一键生成为「我的值得蹬清单」页面（只暴露站点/文章名，不暴露私有内容），本质是把已有的 30 个收藏行为变成 30 条可分享的内容。
- **投票理由**：投票时可选填一句「为什么值/不值」，聚合到站点页。

**为什么有效**：它不要求用户「生产内容」，只要求他把**已经在做的动作**留下痕迹。零边际成本。

**代价**：需要新表（search_log、vote_reason）；隐私要明确（搜索词不关联账号）。

---

### 4.4 冷启动的执行顺序（一句话版）

> **先让站看起来是真的（M0：清 demo），再让写的人不被劝退（M2），再给一个 30 秒能完成的动作（M1），然后给身份（M4），最后才是求长文（M3）。**

今天的问题是顺序反了：产品先做好了「写长文」的完整链路（还带 Markdown 预览），却把「一句话」和「被拒绝后怎么办」两条最基础的路径漏掉了。

## 5. Token 积分体系设计

### 5.1 现状（先把事实钉住）

| 项 | 值 | 出处 |
|---|---|---|
| 初始积分 | 120 | `server/src/auth.ts:13` `INITIAL_TOKENS = 120` |
| 每日签到奖励 | `10 + min(streak, 7)`，即第 1 天 11、第 7 天起每天 17 | `server/src/service.ts:531` |
| 连续 30 天累计 | 约 **489**（11+12+…+17 + 17×23） | 计算 |
| 唯一写入点 | `server/src/service.ts:535`（只 `+`） | 全仓无任何扣减 |
| 消耗入口 | **不存在** | `shared/src/routes.ts` 里唯一的 DELETE 是吊销 Agent 凭证（:10） |
| 签到限流 | 5 次/小时（进程内） | `server/src/app.ts:64` |
| 投票/收藏限流 | 共用每用户 30 次/分钟 | `server/src/app.ts:69,251` |

**问题不是「积分没用」，是「积分在通胀」**：22 个账号 × 120 初始 ≈ 2640 分已经凭空发出；一个活跃用户一个月能攒到 600 分，而全站没有任何东西的价格标签。等到真要加消耗时，早期用户手里的余额已经大到无法定价。

**所以第一件事是「止血 + 立账本」，第二件事才是「上货架」。**

### 5.2 三个方案

#### 方案 A｜身份与展示（只花在「看起来是谁」上）

| 兑换物 | 定价 | 说明 |
|---|---|---|
| 自定义称号（≤6 字，需审核，含违规词库） | 500 / 永久 | 出现在评论、文章、主页 |
| 头像框 / 昵称配色（3 套预设） | 300 / 永久 | 不做上传，规避存储与审核成本 |
| 主页置顶一句自我介绍 | 200 / 30 天 | |
| 精选评论文案样式 | 150 / 30 天 | 只是样式，不改变排序 |

**优点**：零数据风险，纯装饰，绝不会影响任何数值指标。
**缺点**：对 B（采购）和 D（自动化）毫无吸引力；如果站内还没有「值得炫耀的身份」，装饰品卖不动。**它依赖 M4（作者主页）先存在。**

#### 方案 B｜能力与效率（推荐为主）

| 兑换物 | 定价 | 说明 |
|---|---|---|
| 提高待审投稿上限（20 → 40），30 天 | 200 | 现有硬限制是 `MAX_PENDING_POSTS = 20`（`service.ts:63`） |
| 单次投稿优先审核（承诺 24h 内出结论） | 80 / 次 | **只影响时间，不影响结论**；管理员仍可否决 |
| 额外签发 1 个 Agent 凭证（突破 5 个上限），30 天 | 300 | 直击 D 角色痛点 |
| 导出对比表（CSV / JSON） | 60 / 次 | 直击 B 角色痛点（"能交差"） |
| 保留已撤回文章的历史版本（可回滚） | 400 / 永久 | 配合"文章可编辑"（缺口 2） |
| 站内「避坑提醒」置顶一次（限本人发布的内容） | 100 / 次 | 只是把**自己的内容**在**自己的页面**上提一下，不是买位置 |

**优点**：每一项都对准一个具体角色的具体阻塞；不触碰任何评分/排序/审核结论。
**缺点**：需要改配额逻辑（把常量换成按用户读取），有一定实现成本。

#### 方案 C｜实物与外部权益

周边、贴纸、邀请码、合作站的兑换码。

**优点**：感知价值最高。
**缺点**：需要采购、发货、客服；**且"合作站兑换码"极度危险**——它等于用积分把用户导向某个站，与「不接受付费改动」的可信度直接冲突。建议**只保留"邀请码"这一项**（用积分换一个 Agent 凭证邀请码，替代物其实是能力而非商品）。

### 5.3 推荐：**B 为主 + A 为辅，C 只留邀请码**

**理由**：
1. **B 的每一项都对应本文 §1 里一个角色的具体阻塞**，有明确的需求方，不需要"教育用户去用"。
2. **A 是 B 的粘合剂**：能力兑换是"用掉"，身份兑换是"留下"。没有 A，积分花完就归零，用户不会为下一次攒；没有 B，A 只是装饰，攒分没有动力。
3. **C 的实物会让产品从"工具"变成"电商"**，而本站连一次发货流程都没有，现阶段纯负债。

**定价锚点**：按**止血后**的产出校准，即「一个月活跃签到 ≈ 290 分」（基础 5、连续加成上限 5：前 5 天 6+7+8+9+10=40，其余 25 天每天 10，共 290）。这意味着：
- 60~80（导出 / 优先审核）≈ 一周签到 → 随手可换，形成习惯；
- 200 / 300 ≈ 半个月到一个月 → 有目标感；
- 400~500（称号 / 版本回滚）≈ 1.5 个月 → 长期目标。

> 若不动发放、只按现状锚定（月产出 489），则所有价格要按 1.7 倍上浮，而"一个月就能换称号"会让称号迅速贬值。**先止血再定价**，否则定价永远追不上通胀。

**同时必须调整发放（止血）**：
- 初始积分 **120 → 20**（`auth.ts:13`），或改为「完成简介 + 首次投票 + 首次收藏」各发 20，把初始分变成引导动作的奖励——这直接把「注册即通胀」变成「注册即上手」；
- 签到基础 10 → 5，连续加成上限 7 → 5（`service.ts:531`），月度产出 489 → 290 分；
- 对已发出去的存量**不回滚**（回滚会伤到早期用户），但用「过期」消化：**积分 180 天滚动过期**，并在 `/me` 显示到期时间。

### 5.4 防刷

| 风险 | 现状 | 建议 |
|---|---|---|
| 脚本签到 | 5 次/小时限流（`app.ts:64`），但一天只能签一次，限流只防重放 | 保留；**关键是不要让签到成为主要收入来源**（见上：基础降到 5） |
| 多账号刷初始分 | 注册无 IP 维度硬上限（有登录/注册限流） | 初始分走「行为奖励」而非「注册即发」，多开无收益 |
| 刷投票换积分 | 投票/收藏共用 30/min 限流 | **投票本身不发分**（只发"被投票"的分，见下） |
| 刷内容换积分 | 投稿上限 10/h、待审 20 条 | **只在"审核通过"后入账**，pending 不发；被举报成立则**倒扣** |
| 通胀失控 | 无账本，无法审计 | 新增 `token_ledger(handle, delta, reason, refId, createdAt)`，`service.ts:535` 改为写流水 + 更新余额；`/me` 显示「最近积分明细」（透明化本身就是防刷） |

**倒扣规则（防"为了积分乱投"）**：审核被拒 **-10**；被举报并确认的广告内容 **-100** 且 30 天内不可兑换；连续 3 次被拒 7 天内不可投稿。这比"增加审核人力"便宜得多。

### 5.5 与「不编造数据、不写绝对价格」的兼容性检查表

| 兑换物 | 是否影响 score/rank/lowestRate | 是否影响审核结论 | 是否可能变成"花钱买排名" | 结论 |
|---|---|---|---|---|
| 优先审核（80） | 否 | **否**（只影响时间，管理员可见"该条为积分加急"并仍可否决） | 否 | ✅ |
| 提高待审上限（200） | 否 | 否 | 否 | ✅ |
| 额外 Agent 凭证（300） | 否 | 否（Agent 仍强制 pending，见 `agent-api.ts`） | 否 | ✅ |
| 导出对比（60） | 否 | 否 | 否 | ✅ |
| 称号 / 头像框（300~500） | 否 | 否 | 否 | ✅ |
| **站点推荐位** | 会 | — | **是** | ❌ 永不做 |
| **"置顶好评"** | 会 | — | **是** | ❌ 永不做 |
| **合作站兑换码** | 间接 | — | **是** | ❌ 永不做 |

## 6. 优先级建议

### 6.1 排序原则

`价值 = 它解除的是「多少人 × 多硬的阻塞」`；`成本 = 触碰的数据模型改动量`。
本文把 10 个已识别缺口 + 调研中新发现的 6 项一起排。**排序依据不是"功能大小"，而是"它是否让回路闭合"**。

### 6.3 三个批次的实际含义

**批次 P0（3~4 天，先止血）**
`purge:demo` → 驳回理由 → 文章编辑/删除 → 评论自删 → 举报入口。

做完这一批，产品从「有人投稿会被无声拒绝」变成「投稿有反馈、写错能改、看到问题能报」。**这一批不新增任何内容，但它是所有后续机制的前提**——在一个"拒绝不解释"的社区里，任何激励都是空转。

**批次 P1（2 周，让轻表达成立）**
一句话反馈 → 最后确认时间 + 起充额 → 对比页 → 作者主页 → 我的投稿合并 → 时效文案。

做完这一批，A 角色能在 30 秒内留下信息、B 角色能并排算账、C 角色有可分享的主页 URL。**这是「内容从 0 到 1」真正发生的批次。**

**批次 P2（2~3 周，让回报与分发成立）**
积分账本与消耗 → 头像 → 搜索日志 → 缺稿清单 → SEO。

**批次 P3（按需）**
关注/通知 → 注销 → 图片上传 → offers 双价。

### 6.4 关于 SEO 的一个陷阱（必须写清楚）

要求里写「零 SEO：无 sitemap.xml、无 RSS、无 OG」。但**只补这三样是无效的**：

`server/src/static.ts:41-46` 的 SPA 回退对所有非静态路径都返回同一个 `index.html`，而 `web/index.html:3-9` 里只有一条固定的 title/description。React 19 的 `<title>` 是**客户端 hoist**，爬虫（不执行 JS）看到的永远是 `<div id="root"></div>` + 「演示数据为虚构」。

所以正确的顺序是：
1. 服务端在回退时按 `path` 注入 title/description/OG（需要一份 path→meta 的映射，数据可从 store 读）；
2. **`/sitemap.xml`、`/feed.xml`、`/robots.txt` 必须注册在 `mountWeb()` 之前**——`static.ts:28` 的 `app.on(['GET','HEAD'], '*')` 是 catch-all，注册晚了会被 SPA 回退吞掉（README 里已有类似教训：「`compress()` 必须注册在任何路由之前」）；
3. OG 图可以用现成的封面组件（`visuals.tsx` 的 `PostCover`/`StationTile`）的静态版本，不必新设计。

**先做 1，2 才有意义。**

## 7. 三个最重要的结论

### 结论一：冷启动的瓶颈不是「没人愿意写」，是「产品把最短的那条路堵死了」

真实用户手里的信息 90% 是「充了 10 块，第二天 502」这种 20 个字。产品唯一的表达入口是 2000 字评论和 4 字段长文（`Comments.tsx:12`、`Submit.tsx:240-262`），于是这些信息**在产生的那一刻就流失了**。
→ **站点页的一句话反馈（M1）是把转化率从 0 拉到非 0 的唯一动作**，而它不需要任何新数据能力、不违反任何诚信约束。

### 结论二：唯一一次真实投稿的失败是产品事故，不是内容事故

审核台文章页签没有理由输入框（`Admin.tsx:484-512`），服务端只写 status（`moderation.ts:43`），`reviewReason` 在文章通道根本没有落地位置（`service.ts:481`），强制理由只对 agent 通道（`submissions.ts:930`）——**站内用户是全场唯一一个被拒绝后拿不到原因的通道**。
→ 修复成本一天。不修，则所有激励设计都建立在一个"拒绝不解释"的地基上。

### 结论三：在补任何功能之前，先让站点看起来是真的

生产 15 个站里 12 个是「虚构·XX」，全站页脚常驻「不构成消费建议」（`format.ts` 的 `SITE_NOTICE`）。README 早就写明「切模式不清理已有数据，要清用 `pnpm purge:demo --apply`」——**这个命令还没跑**。
→ 一个访客看到满屏「虚构」，不会成为贡献者；一个贡献者写完，也没有真实读者。**这是所有机制失效的共同前提，且只值一条命令（先备份）。**
