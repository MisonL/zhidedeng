## 0. 一句话结论

**不缺功能，缺回路。** 十个缺口里真正该先做的是四个「让已有行为能被表达和收回」的小功能（举报、评论自删、文章撤下、头像），其余六个要么缺证据、要么有前置条件、要么成本远超收益。

必须先纠正一个更根本的判断：生产上只有 1 篇真实投稿且被驳回，而**唯一的贡献者在结构上拿不到驳回原因**。在这个问题上加任何激励、榜单、通知都是空转。

## 2. 事实校正

调研之间冲突、或调研与代码冲突的地方，以代码为准。以下每条都已实地比对。

### 2.1 关于 `POST /api/posts` 的写入路径（已订正）

调研阶段本节曾断言「codex 说错、spec 对」：`Service.createPost()` 直接 `store.put`，
站内投稿有两条并存写入路径。**该结论后来被推翻，本节已按 final 实现重写。**

现行事实（实现已收敛为一条路径）：

- `POST /api/posts` 的路由（`app.ts:779` 起）调用 `enqueueSubmission`，先入 `submissions` 队列，
  审核通过时才物化成 `entities` 里的文章，且**用投稿 id 当文章 id**（`submissions.ts` 的 `materialize`）。
- 曾经存在的 `Service.createPost()`（直接 `store.put`）在路由改造后已无人调用，属于死代码，
  批次 0 已删除。`docs/spec.md:64` 也已同步订正为「公开 POST /api/posts、补录模型、推荐站点都走 enqueueSubmission」。
- 因此**不存在两条并存的站内投稿写入路径**。「编辑必须走队列否则会新建重复文章」的担忧现在对站内投稿普遍成立。
  设计文章编辑时一律以队列为唯一入口；已物化的文章是编辑的**对象**，不是另一条投稿路径。

> 保留这一段修订记录是为了说明：`next-phase-plan` 与 `spec` 曾有矛盾，若日后看到 research 存档
> （`docs/research/research-tech.md`）里还引用旧说法，以本节与现行代码为准。

### 2.2 rs-tech 说错的一条（重要）

rs-tech 的 F10（账号注销）草案写：

```sql
UPDATE entities SET id = ?, data = json_set(data,'$.authorHandle', ?)
WHERE kind='post' AND json_extract(data,'$.authorHandle') = ?
```

**一个账号有多篇文章时，这条语句会把它们全改成同一个 id，直接违反 `entities` 的 `(kind, id)` 主键。**

正确写法是只改 `data` 里的 `authorHandle`，**保留文章自己的 id**——文章 URL 依赖它，改 id 等于改链接。

### 2.3 rs-tech 漏掉的一条（重要）

rs-tech 建议用 `ensureEntityColumns()` 给 `entities` 补新列，但没说要**同时**把列写进 `SCHEMA`。

`server/src/node-app.ts:31-36` 的逻辑是：

```ts
const hasEntities = db.prepare("SELECT 1 FROM sqlite_master WHERE ... name = 'entities'").get();
if (hasEntities) { /* 补 removedAt */ }
db.exec(SCHEMA);
```

新库 `hasEntities` 为 false，**跳过补列分支**，随后由 `SCHEMA` 建表。因此任何新列必须**两处都加**：`SCHEMA` 里（新库）和 `ensureXxxColumns`（老库）。只加后者，新库会缺列。

### 3.1 关于 compose 与生产不一致

rs-ops 指出：仓库 `docker-compose.yml:14` 绑 `127.0.0.1:8788`，而生产实际是 `172.16.81.4:8788`（局域网可达），且 `README.md` 已按后者描述。两份文档互相矛盾，说明生产机上被手工改过且没回填仓库。

## 4. 十项功能的取舍

排序原则不是「功能大小」，而是**它是否让一个已经存在的回路闭合**。

| # | 功能 | 结论 | 依据 | 前置 |
|---|---|---|---|---|
| 1 | **举报入口** | ✅ **做**（最小闭环） | 三份调研一致。这是唯一「用户发现问题→平台知道」的通道，现在完全没有。不做自动下架——判定权交给匿名用户等于让组织化举报下架竞品的真实差评。 | P0-1、P0-4 |
| 2 | **评论自删** | ✅ **做** | 用户控制的最基本一项，成本最低（~150 行 + 测试）。用墓碑保留上下文，但**按任何子行（含隐藏）判断能否物理删**。 | P0-5 |
| 3 | **文章撤下（作者自删）** | ✅ **做** | 比编辑小得多，复用 `removedAt`。必须区分「作者自删」与「管理员下架」，且**不能声称物理删除**（正文仍在 `entities.data` 里）。 | P0-5 |
| 4 | **头像（预设）** | ✅ **做** | 成本 ~110 行。`User.avatar` 字段早就在、`updateMe` 却不接收它，前端已有首字母色块兜底。**只做预设 key，不做上传、不做外链**：CSP 是 `img-src 'self' data:`（`static.ts:12`），外链会被浏览器直接拦掉；base64 塞进 `avatar` 会随每篇文章、每条评论、每个榜单项一起返回，是平方级的传播成本。 | — |
| 5 | **站点对比** | ✅ **做**（轻量版） | 对「导购」定位价值高。但先复用现有 `getStation` 逐个取，**不新建聚合接口**——3 个站 3 次请求足够，等真慢了再聚合。必须：同口径才比、全空值列隐藏、**显式排除 demo**。 | P0-1 |
| 6 | **文章编辑** | ⏸ **推迟** | 三个信源分歧最大。技术上可行但代价不小：要么绕过审核（改 `entities` 直写），要么走队列（要改 `materialize` 加 `editOf` 分支）。更关键的是**动机没验证**：真实投稿只有 1 篇，编辑需求是推测的。**过渡方案**：作者自删（第 3 项）+ 重新投稿，已经能解决「打错字」问题。 | — |
| 7 | **Token 消耗出口** | ⏸ **推迟** | 现在只增不减确实是个半成品，但没有证据表明用户需要兑换。rs-tech 估 490 行、rs-product 估 4~5 天，而**真实用户只有 22 个**。先做一件零成本的事：把 `/me` 里那个只增不减的数字改成有意义的表达（如「签到累计」），避免误导。真要兑换，只能换装饰/身份/额度，**绝不能换排序、投票权重、邀请码或投稿配额**（前两者违背数据诚信，后两者把免费积分变成准入能力）。 | — |
| 8 | **关注 / 通知** | ⏸ **砍掉关注，通知推迟** | 关注需要社交图谱 + 粉丝数 + 刷量防护 + 骚扰处理，四项成本同时出现，而当前连作者主页都没有。通知只保留「与我本人相关」的三类（投稿过审/被拒、评论被回复、举报有结果），用**拉模型**（读时聚合），绝不做写扩散——单进程同步 SQLite 下写扩散会直接卡住事件循环。 | 关注：无；通知：等有稳定内容 |
| 9 | **SEO（sitemap/RSS/OG）** | ⏸ **推迟，但先做两件便宜的** | 单独加 sitemap 是**无效**的：`static.ts:41-46` 的 SPA 回退对所有路径返回同一个 `index.html`，爬虫看到的水远是空 `<div id="root">`。必须先做服务端按 path 注入 meta，那才是主体工作量。**现在就该做的两件**：① `web/index.html:7` 的 description 漏了 AI 采集来源，与 `SITE_NOTICE` 不一致；② 加 `robots.txt` 并在决定清 demo 之前 `Disallow: /`，避免虚构内容被索引后不可撤回。 | 需先定 P0-1 与公开域名 |
| 10 | **账号注销** | ⏸ **定策略后做，排最后** | 合规上是必须的（用户控制 + 数据删除义务），但技术上跨表最多、最易漏：会话外键、文章作者、评论、投票、收藏、投稿、举报、Agent 凭证、通知事件。**且必须先定一个策略**：用户名是否释放（释放则新用户不能继承历史投票，不释放则等于永远占着名字）。rs-tech 草案在这里写错了 SQL（见 2.2）。 | P0-3、以及第 1~3 项 |

这几条价值不低，成本却远低于原十项，建议插队：

| 项 | 为什么值得 | 成本 |

## 5. 批次计划

### 批次 0：止血与前置（2~3 天）

不新增任何功能，只让已有功能不误导人、并为后续解锁。

1. 决定 demo 去留并执行（P0-1）
2. `author()` 降级 + 用例（P0-3）
3. `route()` 支持非 GET path 参数 + 用例（P0-4）
4. `assertPostLive` 统一守卫（P0-5）
5. 驳回理由打通（管理台输入框 → 服务端 → 作者可见）
6. 空态修复、投稿跳转修正、排行榜加站点 tab
7. `index.html` description 与 `SITE_NOTICE` 收敛为同一常量；`robots.txt`
8. compose 绑定地址与 README 对齐

**验收**：`pnpm -r typecheck` + 四包测试全绿；每项高危分支有「改坏即红」的变异记录；生产部署后 `/api/health`、首页、`/admin` 实测通过。

**落地状态（2026-11-25）**：八项全部完成。两处与原计划不同，记下来免得下次又「优化」回去：

1. **P0-1 演示数据去留**：上游运营方决定，本仓库只提 PR、不做数据操作。所以代码侧只做隔离——比价、SEO、来源标签都排除 `source='demo'`，并拒绝举报「虚构内容本身」；但**演示站/演示文章下面挂的真实用户评论仍可举报**（管理员能隐藏它，处置出口是有的）。清库动作留给运营方执行 `purge:demo --apply`。
2. **compose 绑定地址**：没有把生产 IP 硬写进仓库，改成 `BIND_ADDR`（默认 `127.0.0.1`），README 同时写明生产实测绑的是局域网地址、容器形态下管理接口对整个可路由网段可达、唯一的门是 `SYNC_TOKEN`。
3. **P0-5 守卫**：收敛成 `Store.removedAt(kind, id)` 一个入口（原计划的 `assertPostLive` 是同一件事的另一个形状），五处调用点统一走它。

### 批次 1：用户控制（1 周）

1. 评论自删（墓碑 + 子行判断）
2. 文章撤下（作者自删，区分管理员下架）
3. 举报最小闭环（分类 + 人工处置 + 留痕，**不自动下架、不承诺 SLA**）
4. 头像预设（枚举白名单）
5. 统一确认组件

**验收**：新增约 50 个用例；举报的「不自动下架」有测试断言锁住；删父评论的隐藏子回复场景有专门用例。

**落地状态（2026-11-25，分支 `release/agent-submission`）**：四项 + 统一确认组件全部完成，server 868 / web 192 全绿。

实现中与原计划有出入、需要记住的三点：

1. **墓碑不删正文**。原计划写「正文清空」。实际改为「库里保留、接口返回空串」：`reports` 表只存 targetId，不存内容快照，删掉正文等于把举报证据一起删了；而接口侧（`comment()`）对墓碑一律返回 `content: ''`，读者读不到原文。有子行、管理员已隐藏、或正被举报的评论，作者删除时都走墓碑而不是物理删。
2. **`COMMENT_VISIBLE` 加了 `deletedAt IS NULL`**。墓碑是空壳，算进「N 条评论」会让数字虚高；但列表查询仍用 `hidden = 0`，因为别人的回复挂在墓碑下面，得把它取出来渲染成「该评论已删除」。
3. **撤下的连带修复**：`shareCount` 原先没排除 `removedAt`，会出现「分享 3、列表 2」。另外自动通过模式下，撤下后原样重投会幂等命中旧 id、返回 `approved` 而详情 404（幽灵），且飞书同步会把已下架的文章当新文章再发一次——两处都改成「命中已下架的实体时不幂等」，同步那条如实记成 `rejected` 并回报原因。

### 批次 3 落地状态（2026-11-27）

已完成第 2 项「站内通知」：`GET /api/me/notifications`，拉模型，只汇总本人相关的三类事件——投稿审核结果（通过/驳回+理由）、举报处置结果（+备注）、我的文章被下架/恢复。Me 页新增「通知」页签。

几个刻意的取舍：

- **不做未读数**。没有推送通道，红点要么永远不消失、要么永远滞后；两者都比没有更让人困惑。要看的时候点进去即可。
- **全部从既有表派生**，只有「文章恢复」额外记一份 `post_events` 流水——`entities.removedAt` 只存当前状态，恢复会把它清空，历史没别处可存。流水与状态变更在同一个事务里：分开写的话，插流水失败会变成「状态已变、重试 409、通知永久缺一条」。
- **链接只在目标此刻能打开时才给**。下架的文章、被驳回的文章、已删除的模型、已下架的举报目标，一律不给链接——给一个点进去 404 的链接比不给更糟。文章 id 复用 `materialize` 的同一份规则（站内投稿是投稿 id，Agent/飞书是 `sub-<投稿id>`），站点 slug 复用 `findStation` 的认领规则（同 hostname 不同路径是两个站）。
- **标题存快照**。文章后来改了标题，历史通知仍显示当时那篇；通知 id 用流水自增主键，同一毫秒的两条事件不会撞 key。

已完成第 4 项「SEO 主体」：详情页 meta 注入（title/description/canonical/OG）、`/sitemap.xml`、`/rss.xml`、`/robots.txt`。域名未定，所以绝对 URL 的 origin 走 `PUBLIC_ORIGIN` 环境变量，未配置时退回请求自身的 origin（容器里必须配，否则 sitemap 里是内网地址）。

同一条规则贯穿全部四处：**只有真实内容进索引**。演示站与演示文章带 `noindex`（页面给人看，但不该在搜索结果里被当成真实评测）；站内用户写的已发布文章可索引并进 sitemap/RSS；投稿与 Agent 采集的内容带 `noindex` 且不进 sitemap/RSS。登录后页面（`/me`、`/admin`、`/search`）一律 `noindex`。判据收敛成 `indexablePost` / `indexableStation` 两个函数，页面与 sitemap/RSS 共用，避免出现「页面说可索引但不在 sitemap 里」。

其余三项（账号注销、文章编辑、Token 消耗）仍未开始：它们各自需要一个产品决策（用户名与内容归属、编辑与举报版本的联动、Token 兑换什么），不是纯代码问题。

## 6. 明确不做

| 项 | 理由 |
|---|---|
| 头像上传 / 外链 | 对象存储是新子系统（容量、清理、审核、配额）；外链要放开 CSP 等于给每个用户一个向全站读者发起第三方请求的通道 |
| 举报自动下架 | 判定权交给匿名用户，等于给组织化举报一个下架竞品差评的工具，而本站唯一资产是评价可信度 |
| 关注表 + 写扩散通知 | 单进程同步 SQLite 下 5000 粉 = 5000 条 INSERT 阻塞事件循环 |
| Token 换排序 / 投票权重 / 邀请码 / 投稿配额 | 前三者违背数据诚信，后者把免费积分变成准入能力 |
| 评论多级回复 | `parentId` 语义、可见性子查询、UI 缩进全要重写，一层回复已够用 |
| 对比页「推荐最优站」 | 实测指标大多为 null，推荐必然是拍脑袋，且会被当成平台背书 |
| SSR / 预渲染框架迁移 | 服务端注入 OG 已拿到 90% 收益，迁移要重写全部页面与 176 个 web 测试 |
| 通知的邮件 / WebPush | 项目明确不要邮箱（`spec.md:43`），也没有邮件基建 |

## 7. 风险登记（按严重程度）

### R1｜虚构内容被搜索引擎索引后不可撤回

`sitemap.xml` / RSS 一旦上线且包含 demo 内容，搜索引擎抓取后即使清库，索引也会残留数月。且 `sourceLabel()` 对 demo 返回 `null`（2.4），届时**页面上没有任何标记能区分**。

**缓解**：SEO 主体必须排在清 demo 之后；在此之前 `robots.txt` 保持 `Disallow: /`。

> 现状（2026-11-25）：`web/public/robots.txt` 已是 `Disallow: /`，并有一条守卫用例锁住「不能同时出现 `Allow: /`」——之前文档写 Disallow、文件里却是 Allow，两边各说一套。放开抓取的三行写法作为注释留在文件里，等「清完 demo + 有稳定域名」时启用。

### R2｜账号注销的身份串号

如果释放用户名而不改写内容引用，新注册的同名用户会**继承旧用户的文章作者身份、榜单位置、历史投票**。`votes` 表没有外键（只有 `(userHandle, targetType, targetId)` 主键），删不掉也挡不住。

**缓解**：注销功能单独一批上线，逐项核对九张表；加 `retired_handles` 墓碑表；`author()` 先降级（P0-3）。

### R3｜举报成为删差评的武器

不自动下架 → 恶意举报会淹没审核台；自动下架 → 竞品可以举报掉真实差评。而当前是明文 HTTP 且局域网可达，举报人身份可被嗅探。

**缓解**：人工处置 + 处理留痕（who/when/why/what）+ 不对外承诺 SLA + 举报人身份单独存储、不进 `payload`、不进列表默认返回。

## 8. 与数据诚信硬约束的对照

`docs/spec.md` 的「数据诚信」一共 10 条，逐项检查新功能是否越界：

| 硬约束 | 新功能风险 | 处置 |
|---|---|---|
| 不编造实测指标 | 一句话反馈可能被读成平台实测 | 明确标注「用户自述，未经平台核实」，与 `uptime`/`latency` 分开呈现 |
| 不写官方绝对价格 | 对比页可能诱导写出「每月 20 元」 | 只比倍率，不引入货币单位 |
| 必须标注来源 | demo 无标签（2.4） | 对比页与 sitemap 显式排除 demo；补 `sourceLabel` 的 demo 分支或加独立标记 |
| 演示数据不混入真实数据 | 全库 12/15 是 demo | P0-1 |
| 不得花钱买排名 | Token 兑换 | 兑换白名单排除任何影响 score/lowestRate/rank/hot 的项，且有用例锁住 |
| 无实测数据必须 null | 对比页 | 缺失值保持 null，显示「暂无」，不填 0 不填占位 |

1. **注销策略**：用户名是否释放；文章保留还是匿名化；投票保留（计数不变）还是删除（计数下降）

### 9.3 边界声明

本分支交付**代码与文档**，不交付**运营决策**。因此：

- 所有「清数据」「换库」「配证书」「装同步单元」的动作都不在本分支执行，只提供脚本与步骤（`pnpm purge:demo`、README、`deploy/` 单元）。
- 涉及运营才能验证的功能（举报处置流程、通知发送时机）只实现**机制**，不承诺**运营行为**。
- 任何依赖「真实内容量」的设计必须保证**零内容时也不显得坏掉**（见批次 0 的空态修复）。

**复审拦下的五个真问题**（都是独立复现出来的，不是推测）：

1. 一句话反馈「提交→删除→再提交」能无限刷：删除把行删了，配额按行数算就等于退了额度。改成自删留 `deletedAt` 墓碑，配额数含墓碑的行。
2. 游客读一个非空的反馈列表直接 401：`getFeedback` 里用了 `this.user`（未登录抛错），读接口该用 `this.handle`。
3. 评论「发 5 条→全删→再发」绕过每分钟 5 条：无子行的评论是物理删除，数 `comments` 表等于数一个会被删空的集合。改成独立流水表 `comment_writes`，与内容是否被删无关；限流检查、流水、插评论放进同一个写事务，流水每天清一次。
4. 站点详情的 `lastConfirmedAt` 是 null：`getStation` 没把预取表传进去，列表有时间、详情没有。补传并加「列表与详情一致」的用例。
