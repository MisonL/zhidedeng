# zdd-submit Skill

给 AI Agent 用的 skill：分析完中转站后，通过 `zdd` 命令行把数据提交到「什么值得蹬」。

## 安装

Claude Code 会自动读取 `.claude/skills/` 下的 skill。仓库里已经带了这个目录，克隆即可用。

`zdd` 由仓库自带的 `scripts/zdd` 启动，不需要单独安装，目前也没有发布到 npm。
但克隆后要先在仓库根目录跑一次 `pnpm install`——`zdd` 依赖工作区里的
`@zhidedeng/shared`，没装依赖时执行会报 `ERR_MODULE_NOT_FOUND`。
装好之后在仓库根目录登录：

```sh
./scripts/zdd login --key zd_xxx
./scripts/zdd whoami
```

## 设计取舍

**SKILL.md 是给人读的文档，也是给 Agent 读的指令。** 写作时遵循几条原则：

1. **说清边界比说清功能重要。** Agent 最容易犯的错不是不会用命令，而是编造数据。所以「不要做什么」占了很大篇幅。
2. **解释为什么，不只是什么。** 写「不要编造 slug，因为服务端会拒绝且社区数据会失真」，比写「不要编造 slug」有用。
3. **把易混的地方讲透。** 退出码 2（可重试）和 3（改数据）的区别，是这套流程里最容易搞错的地方。
4. **给出判断标准而非规则堆砌。** 最后那条「如果数据被公开展示、用户按它付费了，我担得起吗」比任何字段清单都管用。

## 与 `zdd` 的一致性

`scripts/test/skill.test.ts` 比对文档与实现，覆盖：

| 检查项 | 方向 |
|---|---|
| 子命令 | 双向 —— 文档提到的不存在会失败，实现里有文档没写也会失败 |
| 退出码数值 | 解析文档表格逐行比对，不是子串搜索 |
| 配额数字 | 从 `server/src/agent-api.ts` 的常量反推，逐行比对表格 |
| 禁字段 | 遍历实现集合，每个字段都要既在文档出现、又真的被校验拒绝 |
| 字段字长上限 | 每个 `text(N)` 字段在约束表里都要有自己的行，且该行数字恰好等于 N |
| 示例 payload | 真的跑一遍 `validatePayload`，`modelSlug` 还要核对种子数据 |

**测试是有效的，但覆盖有限**：它只能检查文档里以结构化形式出现的内容（表格、示例、命令名）。散文里的描述——比如「`www.` 不是同一个域名」这类语义断言——它验证不了，要靠人工审查。

「双向」只用在子命令那一行，含义是文档→实现和实现→文档两个方向都查。禁字段那一行不是双向：它遍历实现集合，检查每个字段在文档里出现且被校验拒绝；但文档里多写一个实现没有的字段，这条测试发现不了。

写这条测试时踩过两次同样的坑，都是先被复审指出才发现的：

1. 配额用 `expect(text).toContain(String(value))`，文档里任何位置出现 `10` 都能让「配额 10」通过，改成 15 照样绿。
2. 改完配额，字长检查又只查「这一行里出现过这个数字」——`title/summary/body` 挤在 `100 / 200 / 5000` 一行，把顺序对调测试也不报；`if (!row) continue` 还让整行被删的情况静默跳过。

**「出现过」不等于「对应上」。** 现在是：配额逐行解析出整数后比较相等，字长要求字段各有独立一行且数字集合恰好等于上限，共用行按斜杠位置对齐。
